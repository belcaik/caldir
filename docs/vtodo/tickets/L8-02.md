# L8-02 — website docs

## Responsibility

Document the `--json` widening on the public docs site **alongside** the existing schema, with a second
example object for a task entry, and note task support in the CalDAV provider docs.

## Requirements satisfied

- **R83** (verbatim): *"The `--json` widening MUST be documented alongside the existing schema
  (`website/src/content/docs/commands.md`) with a second example object for a task entry."*
- **C12 (INVIOLABLE as amended)** — the docs must state the migration guarantee exactly as C12 words it:
  *"Every `kind == "event"` entry stays byte-identical; consumer migration is one predicate — selecting
  `kind == "event"` reproduces the old stream exactly."*

## Dependencies

`L7-03` (the schema exists and `T-44`'s fixture is the source for the example) and `L8-01` (terminology,
incl. the Q-2 task-status key name).

## Required context

- `website/src/content/docs/commands.md:112-175` — the `<details><summary>Optional JSON output</summary>`
  block and the single example object. Your second object goes beside it, not instead of it.
- `caldir-cli/src/output/agenda_json.rs` — the shipped struct; the example must be a real serialization, not
  a hand-written approximation.
- `caldir-cli/src/output/agenda_json.rs` `mod tests`, `T-44`
  (`schema_keys_are_stable_over_an_event_and_a_task_fixture`) — copy the task object from that fixture.
- `docs/vtodo/adr/ADR-10-cli-display.md` §D6 — the additive-key table and the compatibility verdict; the
  prose you write is a plain-English rendering of it.
- `website/src/content/docs/providers.md:77-86` — the "Other CalDAV server" section.
- `docs/vtodo/spec.md` §13 R70–R73 — Google/Outlook/webcal are **not** getting task support; the docs must
  not imply otherwise.

## RED tests

**None.** Verification is the website build plus a by-hand diff of the example object against `T-44`'s
fixture. If the example and the fixture disagree, the example is wrong.

## Acceptance criteria

1. The existing event example object in `commands.md` is **kept** and updated only by the five additive keys
   (each `null` on an event) — its pre-existing keys and values are otherwise untouched.
2. A **second** example object is added showing a task entry: `kind: "todo"`, a `due` value, `start` and
   `availability` possibly `null`, `end: null`, the task-status key populated, and an `instance_id` carrying
   the `VTODO:` sigil while `uid` stays bare.
3. Both example objects have the **same key set**. A reader can see the uniform shape at a glance — that is
   the point of the pair.
4. Prose states, in the docs' own voice: no key removed, renamed, or retyped; `null` appears on `start` /
   `availability` only for `kind == "todo"`; `status` keeps its existing value set and the true task state
   lives in the task-status key; the migration predicate is `select(.kind == "event")`.
5. Prose notes that `--json` always includes undated tasks, while the text view counts them in a footer and
   lists them only with `--undated`. Text and JSON deliberately disagree on cardinality (ADR-10 D3 / Q-1).
6. `providers.md` notes that tasks (VTODO) sync via the generic CalDAV provider, and states plainly that
   Google, Outlook, and webcal do **not** support tasks (R70, R86, R91).
7. The website builds clean.
8. Terminology matches `specs/caldir.md` §To-dos — same word for the task status key, no third synonym.

## Non-goals

- Documenting the `_task__` filename convention (that is `specs/caldir.md`, `L8-01`).
- Documenting the RPC protocol changes (no wire change ships — R52/R55; `Method` gains no variant).
- A "tasks" tutorial page, a migration guide, or a changelog entry.
- Promising Google Tasks / Microsoft To Do support (R86 — explicit non-goal, needs new OAuth scopes and
  re-consent for every existing user).

## Notes for the implementer

- **Trap — replacing the event example.** R83 says *alongside*. A reader upgrading needs to see that their
  existing object did not change; deleting it removes the evidence.
- **Trap — inventing the JSON.** Serialize `T-44`'s fixtures and paste the real output. Hand-written JSON in
  docs drifts from the code on the first refactor and is unverifiable.
- **Trap — implying capability negotiation exists.** ADR-07 was CUT entirely (R91): there is no config field,
  no capability probe, no nicer error. Pushing a task to Google/Outlook aborts that calendar's push with
  `expected 1 event(s) in ICS, found 0` — ugly, and **not** data loss. Document the limitation, not a
  mechanism.
- **Trap — `supported-calendar-component-set`.** Do not mention it as a feature. R92: advisory only, never
  an enforcement point; recorded in `L8-06`, not implemented.
