# L1-05: pin the documented loss set

**PR-2.** **Tests only — this ticket adds no production code.**

## Responsibility
Assert that the set of properties `Todo` drops on a write is **exactly** the documented one, and pin
the known `RELATED-TO` collapse as a deliberate, recorded loss rather than an accident. These two
tests are what make R15's user guarantee checkable instead of aspirational.

## Requirements satisfied
- **R15** — *"The user guarantee, for the spec and docs, MUST be: *caldir round-trips a task's modelled properties plus every `X-` property verbatim, parameters included; any other property — `CATEGORIES`, `GEO`, `RELATED-TO`, `RESOURCES`, `COMMENT`, `CONTACT`, and any other IANA or vendor property caldir does not model — is dropped the first time caldir writes that item, on disk and on the server alike, exactly as it already is for events.*"*
- **R87** — *"**Task hierarchies / `RELATED-TO` / subtasks.** The parser collapses them: `MULTIS` lists the ABNF placeholder `"RELATED"`, not `"RELATED-TO"`, so two lines in yield one out with `PARENT` silently gone (verified)… Radicale holds both values with `RELTYPE` params intact (probe Q-F2), so the loss is **100% caldir's parser**. A single `RELATED-TO` survives unmodelled at zero cost; the loss MUST be pinned by a test (T-16)."*
- **R88** — *"**`CATEGORIES`.** Modelling it through the crate **corrupts** it: `WORK,URGENT` becomes `WORK\,URGENT` (verified, pinned `=0.17.10`), turning two categories into one for every third party — flipping it IN via the typed path is *worse* than dropping it; a correct implementation needs a hand-rolled emitter."*

`L1-03`, `L1-04` (both parse and serialize must exist to observe a loss).

## RED tests
Both new, both live in `caldir-core/src/todo.rs`'s test module.

- **ADD** `todo::tests::two_related_to_lines_collapse_to_one` (**T-16**, R87). Feed the two-line
  `RELATED-TO` fixture through parse → serialize and assert the **observed** collapse: two lines in,
  one out, `RELTYPE=PARENT` gone. Right proof: this is a *known loss being pinned*, not a bug being
  fixed. If a future crate upgrade silently changes the behaviour, this test fires and forces the
  question back into the open instead of letting the round trip drift.
- **ADD** `todo::tests::dropped_property_names_are_exactly_the_documented_list` (**T-17**, R15/R23).
  Build (or take from `L0-04`) a VTODO carrying one instance of every OUT property plus an `X-` property
  with parameters, run parse → serialize, and assert:
  1. the set of property names present in the input but absent from the output is **exactly** R15's
     list — no more (a surprise drop), and no fewer (a property we thought we dropped but silently
     mangle instead);
  2. every modelled property and the `X-` property, **including its parameters**, survives verbatim.
  Right proof: R15 is a *promise to users*, and the only way a promise about a set is checkable is by
  asserting set equality in both directions. An `assert!(!output.contains("GEO"))` spot-check would
  pass while an undocumented eleventh property quietly vanished.

## Acceptance criteria
1. `two_related_to_lines_collapse_to_one` passes and its comment states this is a pinned known loss
   (cite R87 and probe Q-F2: Radicale holds both values, so the loss is caldir's parser). (T-16)
2. `dropped_property_names_are_exactly_the_documented_list` passes and asserts **set equality**, not
   containment, against R15's list. (T-17, R15)
3. `X-*` survives with parameters intact — the one thing R15 promises beyond the modelled set. (R23)
4. Zero production lines changed in this ticket.
5. `just check` and `just test` green, 686 baseline unmodified. (R104)

## Non-goals
- **Do not fix either loss.** `RELATED-TO` and `CATEGORIES` are OUT by ruling (ADJUDICATION C-2). A
  hand-rolled `CATEGORIES` emitter is a follow-up ADR **for both kinds together** (R88); re-encoding
  `RELATED-TO` as `X-CALDIR-RELATED-TO` inherits the identical defect (R87) — do not attempt it.
- **Do not** add fields to `Todo`, change the codec, or "improve" the parser to notice OUT properties.
- **Do not** edit `specs/caldir.md` — `L8-01` owns the doc half of R15/R16 and is reviewed against
  T-17's list.
- No `CalendarItem`, no arity rules, no disk or wire work.

## Notes for the implementer
- Write T-17's expected list as a **named constant in the test** spelling out R15's names, so
  `L8-01`'s doc amendment can be diffed against it literally. Spec §18 records T-17 as the citation
  handle for that review.
- The `RELATED-TO` mechanism, for your test comment: `MULTIS` lists the ABNF placeholder `"RELATED"`,
  not `"RELATED-TO"`, so the parser folds the two lines into one and drops `PARENT`. Verified.
- Compare **parsed/derived sets or property names**, never whole-document bytes: `DTSTAMP` is
  re-stamped on every serialize (R25), so a byte comparison is permanently red.
- **Probe hygiene (R108)** if you verify any of this with a scratch crate: pin
  `icalendar = "=0.17.10"`, print the resolved version, echo the exact input bytes sent. Two probes in
  this effort produced wrong answers from unexamined inputs. *A probe that returns the answer you
  expected is not evidence until you have inspected the input it actually sent.*
- Conventions: inline `#[cfg(test)] mod tests`, no fixture files,
  `use pretty_assertions::assert_eq;`. CI: `-D warnings` on `just check`; TZ matrix on `just test`.
