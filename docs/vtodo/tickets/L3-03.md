# L3-03 — kind-aware diff computation

> Layer L3 · PR-2. Sibling of `L3-02`; both edit `calendar_diff.rs`, so land one, rebase the other.

## Responsibility

Make `CalendarDiff::compute` component-aware:

1. The local id set and the **remote map** are keyed by the kind-carrying identity from `L1-06`,
   closing R36 hazards 1–4 — no state-file collision, no mis-keyed `Update` overwriting one
   component with the other, no double delete, no base ping-pong.
2. Both `Cancelled` skip-rules key on **`CANCELLED` only, never `COMPLETED`**.
3. The direction machinery is **unchanged**: three-way against the stored base first, mtime /
   `LAST-MODIFIED` only as a fallback, Push-biased `(Some, None)` retained.

## Requirements satisfied

- **R36 (INVIOLABLE), hazards 1–4.** *"Item identity MUST carry the component kind:
  `(kind, uid, Option<recurrence_id>)`."* Hazard 2: *"the remote map is built by `.collect()`
  (`calendar_diff.rs:25-28`), so two same-UID remote items become one; pass 1 then compares a
  local task against a remote event … and emits an `Update` … that **overwrites one component
  with the other** — worse than a delete."* Hazard 3: *"pass 1 runs once per local file and
  `sync_bases.get(&id)` (`:86`) is true both times, so **two** deletes fire though one identity
  was tracked."*
- **R40.** *"Direction MUST use the existing machinery unchanged: three-way against the stored
  base first (`calendar_diff.rs:153`, `:161-167`), mtime / `LAST-MODIFIED` only as a fallback."*
- **R41.** *"The Push-biased fallback for an item with no `LAST-MODIFIED` and no `SEQUENCE`
  (`(Some, None) => true`, `calendar_diff.rs:187`) MUST be kept for tasks. Wrong-Pull destroys
  the user's local edit with no recovery."*
- **R42.** *"Both skip-rules keying on `Cancelled` (`calendar_diff.rs:45` 'both cancelled' and
  `:106` 'missing locally + remote cancelled') MUST key on `CANCELLED` **only**, never
  `COMPLETED`. If `COMPLETED` shared the `:106` rule a remote completed task would **never be
  created locally** — and the MVP's own fixture is `STATUS:COMPLETED`."*
- **R99 (A-5).** *"A task present in a non-empty remote task list on a previous sync, absent
  from the current one, with a known base, MUST produce an incoming delete."*
- **R100 (A-6).** *"A directory holding a VEVENT file and a VTODO file sharing a UID MUST
  produce two identities, two base entries, two `known_event_ids` lines, two base files, **no**
  `doctor` duplicate warning, and … exactly **one** delete against the correct file."*

## RED tests

All in `caldir-core/src/diff/calendar_diff.rs`'s inline `#[cfg(test)] mod tests`.

**`T-27`** — `…::a_task_omitted_from_a_non_empty_remote_list_is_still_deleted`.
Remote list is **non-empty** and contains at least one task, but not this one; the task has a
known base. Asserts exactly one `EventChange::Delete` in `incoming`. *Why:* A-5/R99 — absence
must stay meaningful. This is the test that fails if someone over-generalises `L3-04`'s belt.

**`T-28`** — `…::a_remote_completed_task_absent_locally_is_created_and_both_cancelled_drift_is_ignored`.
Two assertions in one test: a remote `STATUS:COMPLETED` task absent locally with no base yields
one `incoming Create`; two items both `STATUS:CANCELLED` with drifted fields yield no change.
*Why:* R42 — if `COMPLETED` ever joins the `:106` rule the MVP's own demo fixture silently
fails to pull.

**`T-31`** — `…::a_shared_uid_pair_produces_exactly_one_delete_against_the_right_file`.
One local VEVENT and one local VTODO sharing a UID, neither in the remote list, the **shared**
id known in `sync_bases`. Asserts exactly **one** delete, and that its payload is the item whose
identity is actually tracked. *Why:* R36 hazard 3 + A-6.

**`T-32`** — `…::a_task_with_no_last_modified_and_no_sequence_pushes`.
Asserts the change lands in `outgoing`, not `incoming`. *Why:* R41 — this is existing VEVENT
behaviour and must not silently invert for tasks.

## Acceptance criteria

1. `local_event_ids` and `remote_by_id` are keyed by the kind-carrying identity; a same-UID
   event/task pair yields **two** map entries on each side.
2. Pass 1 never compares a local task against a remote event (or vice versa) — the lookup
   cannot match across kinds.
3. No `Update` can be emitted whose `from` and `to` are different component kinds.
4. Both `Cancelled` skip-rules test `CANCELLED` only; `COMPLETED` appears in neither (R42).
5. `update_direction` and `local_is_newer` are **behaviourally unchanged** — the three-way base
   compare still runs first and `(Some(_), None) => true` is still present (R40, R41).
6. `T-27`, `T-28`, `T-31`, `T-32` exist with exactly those names and pass.
7. `SUITE` green with zero edits to existing event tests (R104).

## Notes for the implementer

- **Trap — `.collect()` into a `HashMap` silently drops duplicates** (`calendar_diff.rs:25-28`).
  With a component-agnostic key, a same-UID event/task pair becomes one entry and the *later*
  one wins non-deterministically. Once the key carries kind this is fixed by construction — but
  only if **every** key-producing call site changes together, including `local_event_ids` `:20`
  and the two `sync_bases.get(&id)` lookups at `:84` and `:110`.
- **Trap — hazard 3 is a *loop* bug, not a key bug.** Pass 1 runs once per local file; with a
  shared identity the base lookup is true on both iterations and two deletes fire. `T-31` pins
  the count, so assert `incoming.len() == 1`, not just "a delete exists".
- **Trap — direction is not yours to improve.** R40/R41 say "unchanged". A tidier tiebreak here
  changes sync direction for every existing user and breaches R2/C2.
- The `#[allow(clippy::large_enum_variant)]` on `EventChange` exists because `Event` is big;
  expect to keep or widen it once the variants carry an item. `-D warnings` is on in CI.
- `test_utils.rs` is crate-private to `caldir-core`; diff constructors live at `:106-128`.
