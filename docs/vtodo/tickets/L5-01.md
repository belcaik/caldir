# L5-01 — fix the pre-existing `find_map(Result::ok)` silent drop

**Layer:** L5 (CalDAV provider) · **PR-2** · **Depends on:** `L4-01`

## Responsibility

`parse_event` in `caldir-provider-caldav/src/caldav/ops.rs:32-37` stops keeping only the first
parseable component and adopts R19's loud behaviour by delegating to the same single-item decoder
`L4-01` gave the RPC wire (`CalendarItem` decode: arity rules + unsupported-component naming +
the R18 `VTIMEZONE` exemption). This is a **pre-existing bug, not a VTODO bug** (spec §14 mode B);
it ships as its own ticket.

## Requirements satisfied

- **R19 (INVIOLABLE)** — *"An unsupported data-bearing component (`VJOURNAL`, `VFREEBUSY`, unknown,
  `X-`) MUST produce a hard error naming the component — never a silent skip, never an empty
  vector. A silent drop feeds the delete path (R48, §15 C7/C10)."*
- **R66** — *"The pre-existing `find_map(Result::ok)` at `caldav/ops.rs:32-37`, which silently keeps
  the first parseable component, MUST be fixed to R19's loud behaviour. Own ticket — a pre-existing
  bug, not a VTODO bug."*
- **R74 (mode-B half)** — *"Both MUST be fixed, and the fix for A MUST NOT introduce B. … B by R19
  (loud on unknown) and R49 (never infer a delete from a task-less response)."*

## Acceptance criteria

1. `parse_event` returns `Result<CalendarItem, _>` (or the crate's `anyhow::Result`), **never**
   `Option`, and contains no `find_map(Result::ok)` or equivalent first-Ok selection.
2. It delegates to `L4-01`'s single-item decoder; no arity or component-name logic is written a
   second time in this crate.
3. The three callers propagate the error rather than skipping the resource: `fetch_events`
   (`list_events.rs:37-43`) returns `Err` for the whole list when any resource fails to decode —
   **a partially-parsed list is forbidden**, because absence is what the delete path acts on (R74).
4. `create_event`/`update_event` read-back (`:53-63` / `:52-62`) may still tolerate a failed
   read-back (it currently falls back to the submitted item via `.ok()`), but MUST NOT convert a
   decode failure into a *different* item.
5. The doc comment at `ops.rs:29-31` no longer claims "we take the first one that parses cleanly
   and silently drop malformed events".
6. The two existing tests at `ops.rs:168-181` are mechanically adapted to the new return type
   (`expect` → `unwrap`, `is_none()` → `is_err()`); **no assertion value changes**, and the
   adaptation is called out in the commit message.
7. `cargo test --workspace --no-fail-fast` is green, including `caldir-provider-icloud`.

## Non-goals

## Notes for the implementer

- **iCloud may light up for free — verify, do not assume.** `caldir-provider-icloud` has *no*
  mapping layer: every command delegates to `caldir_provider_caldav::caldav::ops`
  (`commands/list_events.rs:19`, `create_event.rs:19`, `update_event.rs:19`,
  `delete_event.rs:18`, `list_calendars.rs:18`, `connect.rs:33`). Confirm with
  `grep -rn 'caldav::ops' caldir-provider-icloud/src` before writing anything about iCloud in the
  commit message. **R69 marks every CalDAV statement UNVERIFIED for iCloud** — you may say the code
  path is shared; you may **not** say iCloud task sync works. That gap is recorded by `L5-05`.
- `parse_event` is `pub(super)` (visible inside `crate::caldav`). Changing its return type does not
  break iCloud, which only calls `ops::fetch_events` and friends.
- Trap: `fetch_events` currently does `if let Some(event) = parse_event(…) { events.push(event) }`
  (`list_events.rs:38-42`). Turning this into `?` is the whole point — resist "log and continue".
- Trap: clippy runs with `-D warnings`; an unused `Option` import or a now-dead `find_map` triggers
  a hard failure in `just check`.
- Trap: never run two cargo commands in parallel — `rust-toolchain.toml` pins `1.97.0` and parallel
  invocations race rustup (`docs/vtodo/context/testing.md` §1).
