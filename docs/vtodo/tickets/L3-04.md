# L3-04 — R49 version-skew belt

> Layer L3 · PR-2. One file, one rule, and it is the last guard against a mixed-version wipe.

## Responsibility

In `CalendarDiff::compute`: if the remote response contains **zero tasks** while the local
calendar holds **at least one task with a known base**, skip **all** task incoming deletes for
that run and warn. Pure inference from the data already in hand — **no RPC change**.

## RED tests

**`T-30`** — `diff::calendar_diff::tests::a_task_less_remote_response_suppresses_all_task_deletes`
in `caldir-core/src/diff/calendar_diff.rs`.

Fixture: a local calendar holding **two** tasks with known bases and **one** event with a known
base; the remote list contains the event and **no tasks at all**. Asserts:

1. `incoming` contains **zero** deletes for either task — this is the belt.
2. The event's own delete is **still emitted** — the belt is task-scoped, never a blanket
   suppression. *Why:* over-broad suppression silently disables VEVENT delete detection for
   every existing user, a regression no other test in the layer would catch.

Pair-read with `T-27` (`L3-03`): a *non-empty* remote task list that merely omits one task must
still produce that delete. `T-27` and `T-30` are each other's boundary.

## Acceptance criteria

1. The belt triggers only when the remote task count is **exactly zero** and the local side has
   ≥ 1 task with a known base (`sync_bases.get(&id).is_some()`).
2. When it triggers, **all** task incoming deletes are skipped for that run — both the pass-1
   local-missing-remotely branch and any task-shaped pass-2 branch.
3. Event deletes, task creates, task updates and all outgoing changes are **unaffected**.
4. When the remote list contains ≥ 1 task, behaviour is byte-identical to `L3-03`'s.
5. A warning is surfaced when the belt triggers. The **wording is deferred** (R50) — do not
   invent a `DoctorWarning` variant or a new CLI surface for it here.
6. **No RPC change.** `ListEvents`'s response stays a bare `Vec<…>`; making it an object would
   hard-break installed provider binaries (ADR-08 Decision 3).
7. `T-30` exists with exactly that name and passes.
8. `SUITE` green with zero edits to existing event tests (R104).

## Non-goals

- R48 / C7 (unreadable-file delete suppression) — that shipped in `L0-03`, PR-1. R49 is a
  **different** belt: R48 is about *local* files that failed to load, R49 about a *remote*
  response that carries no tasks. Do not merge them into one flag.
- The warning's final text, placement, or exit-code behaviour (R50, deferred to the CLI ADR).
- Any provider-crate edit, any capability negotiation — ADR-07 was **cut entirely** from the MVP
  (ADJUDICATION). This belt is what replaces it.
- Distinguishing "old provider" from "genuinely empty task collection". The rule is deliberately
  data-only; it cannot and need not tell them apart.

## Notes for the implementer

- **Trap — scope creep into a blanket skip.** The obvious implementation ("if remote is empty,
  emit no deletes") is wrong twice over: it changes VEVENT behaviour, and it fires for a
  genuinely empty *event* calendar. Count **tasks** in the remote list, suppress **task**
  deletes only. Criterion 3 and `T-30`'s second assertion exist for this.
- **Trap — the belt must not swallow the `L3-02` case.** An undated task with a known base and
  an empty remote is already protected by R44+R58 (`T-25`). If you implement R49 in a way that
  makes `T-25` pass *for the wrong reason*, `L3-02`'s protection can later be removed without a
  test going red. Keep them independent; do not delete `T-25`.
- `sync_bases.get(&id)` returns `Option<&Option<Box<Event>>>`: `None` = never synced,
  `Some(None)` = legacy known-id entry, `Some(Some(_))` = full base. "Known base" for R49 means
  `is_some()` — the same test the delete branch itself uses at `:84`.
- Keep the belt's decision computed **once**, before the loops, from the inputs — not
  re-derived inside each branch, where a later edit can desynchronise the two.
