# L2-05 — migrate batch 3: provider crates compile against the new core API

**Layer:** L2 · **PR-2** · **Depends on:** `L2-02` · **Parallel with:** `L2-03`, `L2-04`

## Responsibility

Mechanical narrowing in the provider crates so the workspace builds against the retyped
`caldir-core`. **No behavioural change. No VTODO support added anywhere.**

Like `L2-03`/`L2-04` this is a migrate batch that exists to keep CI green batch-to-batch. Unlike
them it *does* carry two R-numbers — but **in the negative sense**: it satisfies them by *not*
editing provider behaviour.

## Scope — measured

Grep on this branch finds the core-API surface reaching providers in exactly two files:

| Crate / file | What breaks |
|---|---|
| `caldir-provider-webcal/src/commands/list_events.rs:4,16,81` | `use caldir_core::Event;` + two `Event::from_ics_str` calls. |
| `caldir-provider-caldav/src/caldav/ops.rs:7,33` | `use caldir_core::Event;` + `Event::from_ics_str(ics)` inside the `find_map(Result::ok)` chain at `:32-37`. |

The INDEX row additionally names `caldir-provider-google/src/google_event/from_google.rs`,
`caldir-provider-outlook/src/graph_api/types/mod.rs`, and `caldir-provider-icloud/src/**`. Those
files construct/consume `Event` values but do not call the retyped constructors today; **migrate
only what the compiler actually breaks** and report if the reach is wider than the two files above.

Nothing breaks at all until `L2-06` flips `Event::from_ics_str`'s return type. If
`cargo check --workspace` is already clean when you start, say so and land a no-op — that is a
valid outcome for this ticket, and `L2-06`'s reviewer needs to know it.

**You may split further and report back rather than rush.** The legacy accessor keeps each batch
green (INDEX §6.3).

## Acceptance criteria

1. `cargo check --workspace --all-targets` is clean under `-D warnings`. (R70)
2. `git diff --stat` over `caldir-provider-*` shows **only** type/accessor renames and
   narrowings — no new match arms on `CalendarItem::Todo` that do provider work, no new config
   key, no new RPC field, no new warning string. (R70, R73)
3. `caldav/ops.rs`'s `find_map(Result::ok)` at `:32-37` is left **as it is**, bug and all. Fixing

4. `cargo test --workspace --no-fail-fast` green at 686.

## Non-goals

- **Do not** add VTODO handling to any provider. Google/Outlook are structurally VEVENT-bound
  (R70/R86); webcal's VTODO-only-feed silent drop is covered by R49 at `L3-04`, not here (R72).
- **Do not** fix `find_map(Result::ok)` — `L5-01`.
- **Do not** parameterise any `comp-filter` — `L5-02`/`L3-02`.
- **Do not** add a capability field, builder method, or negotiation of any kind. ADR-07 is CUT by
  user decision; shipping a stub of it breaches R73/R91.
- **Do not** improve an error message a provider emits on a task payload. The
  `expected 1 event(s) in ICS, found 0` abort is the **accepted** consequence (R71) and `L6-01`
  pins it in a test.

## Notes for the implementer

- The five provider binaries are discovered on `PATH`; they are independent crates in the
  workspace `members` list. A break in one aborts `cargo check` before the others are reached,
  so fix them in workspace-member order and re-check after each.
- `caldir-core/src/test_utils.rs` is crate-private (`lib.rs:11-12`) — provider crates cannot use
  `VTODO_ICS`. Each provider crate has its own `tempfile` dev-dep and builds fixtures locally.
- If a narrowing would silently drop a non-event item, **stop**: a silent drop feeds the delete
  path (R19/R48, C10). Prefer surfacing the existing error and leaving a `TODO(L5-01)` comment.
- CI runs `-D warnings` via `RUSTFLAGS` in the `check` job. An unused `use caldir_core::Event;`
  left behind after a narrowing fails the build.
