# L5-03 — `409 <C:no-uid-conflict/>` falls back to update

**Layer:** L5 (CalDAV provider) · **PR-2** · **Depends on:** `L5-02`

## Responsibility

On a `409` carrying `<C:no-uid-conflict/>`, `create_event` stops bailing and instead does what the
server is telling it to do: locate the existing resource holding that UID via `find_event_location`
and issue a **conditional PUT** (`If-Match: {etag}`). A `409` is the server's way of saying "this is
an update, not a create".

## Requirements satisfied

- **R63** — *"caldir MUST handle `409 <C:no-uid-conflict/>` on push. Reachable in normal use: a user
  renaming a local `.ics` changes the slug but not the UID, so `create_event.rs:26-38` PUTs to a new
  href with `If-None-Match: *` while the old resource still holds that UID — exactly the rejected
  pattern. Required behaviour: on `409`, fall back to `find_event_location` + a conditional PUT,
  i.e. treat it as the update the rename actually is."*
- **R79** — *"`409 <C:no-uid-conflict/>` on push MUST be handled per R63, not surfaced as an opaque
  HTTP failure."*
- **R103 (A-9)** — *"Renaming a task's local file, then pushing, MUST update the same server
  resource, not surface a `409`."*

## RED tests

1. `caldav::ops::create_event::tests::a_409_no_uid_conflict_falls_back_to_update` **(T-40)**
   — in `caldir-provider-caldav/src/caldav/ops/create_event.rs`, new `#[cfg(test)] mod tests`.
   Against wiremock: the first `PUT {uid}.ics` (with `If-None-Match: *`) answers `409` + the probe's
   exact body; a `REPORT` on the collection answers a multistatus pointing at `other-href.ics` with
   an etag; a second `PUT` is expected **at `other-href.ics`** carrying `If-Match: {that etag}` and
   **no `If-None-Match`**. Asserts: the call returns `Ok`, exactly two PUTs were issued, and the
   second targeted the located href. Why: proves the 409 became an update against the *existing*
   resource rather than a retry against the same href (which would loop forever).
2. `caldav::ops::create_event::tests::a_409_without_no_uid_conflict_is_a_loud_error_carrying_the_body`
   — a `409` whose body does not contain `no-uid-conflict` must still fail, but the error message
   must include the status **and** the response body. Pins R79's "not opaque" clause and stops the
   fallback from swallowing unrelated conflicts.
3. `caldav::ops::create_event::tests::a_412_precondition_failed_is_not_treated_as_a_uid_conflict`
   — guards the adjacent status. `If-None-Match: *` against an existing href yields `412`, not
   `409`; conflating them would turn "someone else wrote first" into a silent overwrite.

## Acceptance criteria

1. `create_event` inspects the PUT response body, not only `parts.status`. Today it discards the
   body (`let (parts, _body) = …`, `create_event.rs:41`) — it must be read and parsed.
2. The conflict is detected by XML **element name** `no-uid-conflict` in the CalDAV namespace
   (`roxmltree` is already a dependency), not by substring matching on serialized XML.
3. On a detected conflict: `find_event_location(&caldav, &calendar_href, calendar_url, uid, kind)`
   (the `L5-02` signature) then a raw PUT to `location.href` with `Content-Type: text/calendar` and
   `If-Match: {location.etag}`. Reusing `update_event::update_event` wholesale is acceptable and
   preferred — it cannot recurse, since update never calls create.
4. The fallback is attempted **at most once**. No loop, no retry-on-409-again.
5. Any other non-success status keeps today's behaviour, with the body appended to the message.
6. The happy path (`201`) is unchanged: same href, same headers, same read-back.

## Non-goals

- No new href scheme, no kind suffix (R62 — the href stays `{uid}.ics`).
- No handling of the multi-component `400` (that is `L5-04`).
- No retry/backoff policy, no `412` recovery.

## Notes for the implementer

- **The 409 is real, but R63's stated trigger does not hold in this codebase — implement the
  requirement anyway, and flag the discrepancy in your PR description.** R63 explains the 409 via a
  local file rename. In this code the href is derived from the **UID**, not the local slug
  (`event_url`, `client.rs:73-76`; used unconditionally at `create_event.rs:26`), so a rename does
  not change the href. The reachable trigger is a **server-assigned filename**: the resource lives
  at some other href, caldir creates at `{uid}.ics`, Radicale answers `409` (probe Q-E.3). That is
  exactly the case `find_event_location`'s REPORT fallback exists for (`ops.rs:47-49`). Same-href
  PUT with `If-None-Match: *` yields `412`, and a plain overwrite yields `204` (probe Q-E.2).
- Live-tier `T-58` (`L5-05`) covers the rename scenario end to end and asserts the **outcome** (one
  resource, updated, semantics preserved) rather than a status code, precisely because of the above.
- Radicale is a **faithful store but not a byte-echo**: it sorts properties alphabetically within a
  component, re-folds at 75 octets, and synthesizes `VTIMEZONE` for any `TZID`. Never assert on the
  bytes it returns from the read-back (R30).
- Trap: `caldav.request_raw` returns `(parts, body)` where the body type is whatever hyper collected
  — read it before the `parts.status` check so the error path can quote it.
- Trap: `just check` runs clippy with `-D warnings`; never run two cargo commands in parallel
  (`rust-toolchain.toml` pins `1.97.0`; parallel invocations race rustup).
