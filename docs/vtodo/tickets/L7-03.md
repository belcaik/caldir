# L7-03 — the `--json` schema widening (C12 as amended)  ⚠ HIGH RISK

## Responsibility

Widen the public `--json` agenda schema to carry tasks **without breaking any consumer of the old stream**.
No key is removed, renamed, or retyped. `start` and `availability` widen `T -> T | null`. Five additive keys
appear on **every** entry. `status` is **not** touched. `--json` always includes undated tasks.

## Requirements satisfied

- **C12 (INVIOLABLE as amended)** — verbatim from `spec.md` §15: *"no key removed, renamed, or retyped;
  `start` and `availability` widen to `T | null` and `null` MAY appear **only** on `kind == "todo"` entries;
  five additive keys (`kind`, `due`, `completed`, `percent_complete`, task status) on every entry so the
  object shape stays uniform; `status` is **NOT** retyped and keeps its existing value set. Every
  `kind == "event"` entry stays byte-identical; consumer migration is one predicate — selecting
  `kind == "event"` reproduces the old stream exactly."*
- **R83** (schema half): *"The `--json` widening MUST be documented alongside the existing schema … with a
  second example object for a task entry."* (The docs half is `L8-02`; this ticket ships the schema the
  docs describe and the fixture they copy from.)

## RED tests

**`T-44` — `caldir-cli/src/output/agenda_json.rs`, `mod tests`:**
`output::agenda_json::tests::schema_keys_are_stable_over_an_event_and_a_task_fixture`

Two fixtures in one test (C12's amended wording requires both):

1. **Event entry** — assert the serialized object's key set is exactly the old key set **plus** the five new
   keys; `start` is a JSON string and **non-null**; `availability` non-null; `end`, `kind` etc. present.
   Assert `kind == "event"` and all five additive keys are `null` except `kind`.
2. **Todo entry** (a DUE-only task, and separately an undated one) — assert the key set is **identical** to
   the event entry's; `start` may be `null`; `availability` is `null`; `end` is `null`; `due` carries the
   DUE; `kind == "todo"`; `status` is present and is a value from the **existing** `Status` value set.

Why one test over both: the load-bearing property is that the two objects have the *same key set*. Asserting
them separately lets a uniform-shape regression through.

## Acceptance criteria

1. No key is removed, renamed, or retyped. Diff `agenda_json.rs` and confirm every pre-existing field name
   and type survives (`start` and `availability` are the only two whose type widens).
2. `start: Option<String>` and `availability: Option<Availability>`; `null` is emitted on those two keys
   **only** when `kind == "todo"`. An event entry can never serialize `null` there.
3. Exactly five additive keys, on **every** entry, so the object shape is uniform:
   | key | type | event | todo |
   |---|---|---|---|
   | `kind` | `"event" \| "todo"` | `"event"` | `"todo"` |
   | `due` | `string \| null` | `null` | DUE, same encoding as `start` |
   | `completed` | `string \| null` | `null` | COMPLETED, RFC3339 UTC |
   | `percent_complete` | `number \| null` | `null` | 0–100 |
   | *task status* | `"needs_action"\|"in_process"\|"completed"\|"cancelled"\|null` | `null` | TodoStatus |
   The task-status key name comes from `specs/caldir.md` §To-dos (Q-2 — see the sequencing block).
4. **`status` is NOT retyped.** It stays the non-optional `Status` enum meaning "is this item live" — the
   sense `is_visible` uses (`output/event.rs:7`). `TodoStatus` maps on: NeedsAction / InProcess / Completed
   ⇒ `"confirmed"`, Cancelled ⇒ `"cancelled"`. The true value lives in the task-status key. Widening
   `status`'s value set instead breaks every consumer matching on it exhaustively and is forbidden by C12.
5. On a todo entry: `end` is **always** `null` (C-2 FORBIDS DTEND); `all_day = anchor.is_date()`, `false`
   when undated; `tzid` comes from the anchor.
6. A todo's `instance_id` carries the `VTODO:` sigil (L1-06); its `uid` stays bare. Event `instance_id`s are
   unchanged.
7. `--json` emits undated tasks (`start: null`, `due: null`). `--undated` does not gate JSON.
8. `jq 'select(.kind == "event")'` over the new stream reproduces the old stream exactly — the stated
   migration predicate. Sanity-check it by hand on a mixed fixture.

## Notes for the implementer

- **Trap — "just make `status` an untagged union".** That is the single most tempting and most forbidden
  change in this ticket. ADR-10 D6: *"Widening `status`'s value set instead breaks every consumer matching
  on it exhaustively — strictly worse than one new key."*
- **Trap — `#[serde(skip_serializing_if = "Option::is_none")]`.** Do **not** add it to the new keys. C12
  requires the object shape to stay **uniform**: every key present on every entry, `null` where absent.
- **Trap — synthesizing a `start` for a DUE-only task.** That is the mission's forbidden fake event; ADR-10
  lists it under §Rejected because.
- **Trap — the flatten.** `EventJson` is `#[serde(flatten)]`ed into `AgendaJson` (`:39-40`); key collisions
  between the two structs serialize silently. Put each new key in exactly one of the two structs.
- `From<&Event>` at `:81-103` destructures exhaustively — mirror that style for the todo arm so a future
  field addition is a compile error, not a silent omission.
- Toolchain `1.97.0`; clippy `-D warnings`; CLI text tests use `indoc`.
