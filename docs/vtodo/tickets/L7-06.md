# L7-06 — `caldir new` stays event-only

## Responsibility

Tests only, plus whatever narrowing the type change forces. Pin **R90**: `caldir new` creates VEVENTs and
nothing else. No `--due` flag, no task creation, no task template. Tasks arrive by pull or by a
hand-authored `.ics`.

## Requirements satisfied

- **R90** (verbatim): *"**`caldir new --due`.** No ADR owns it; tasks arrive by pull or hand-authored `.ics`.
  `caldir new` continues to create events only."*
- **C13** (INVIOLABLE) for `new`'s existing output and exit codes.

## Dependencies

`L2-04` (CLI call sites migrated to `CalendarItem`).

## Required context

- `caldir-cli/src/commands/new.rs` — the command and its existing `mod tests`. Read the test module's
  conventions before adding to it; it is the largest CLI command file (655 lines).
- `caldir-cli/src/main.rs` — the `New { … }` clap variant and its dispatch arm; the flag list is the thing
  the new test asserts over.
- `docs/vtodo/adr/ADR-10-cli-display.md` §D7, `new` row: *"creates VEVENT only; no ADR owns `caldir new
  --due`. Tasks arrive by pull or hand-authored `.ics`"* — marked **deferred**, not MVP.
- `docs/vtodo/spec.md` §16 (Non-goals) R90.

## RED tests

**`caldir-cli/src/commands/new.rs`, `mod tests`:**
`commands::new::tests::new_still_creates_only_events`

Run the `new` command end-to-end into a temp calendar and assert on the **file it wrote**:
1. the bytes contain `BEGIN:VEVENT` and **do not** contain `BEGIN:VTODO`;
2. the file loads back as a `CalendarItem::Event` (assert on the variant, not on a summary — the variant is
   the thing R90 pins);
3. the written filename has **no** `_task__` prefix (`L1-07`'s reserved task-filename convention), i.e.
   `new` cannot accidentally produce a name the loader will treat as a task.

Assertion 1 is a negative byte assertion on purpose: it is the cheapest thing that fails loudly if someone
later wires a task template into `new`.

Add, to pin the CLI surface itself:
`commands::new::tests::new_has_no_due_flag` — assert via the clap command definition (`Command::debug_assert`
or by iterating `get_arguments()`) that no argument named `due` exists on `new`. A prose non-goal is not a
guard; this is.

## Acceptance criteria

1. `commands::new::tests::new_still_creates_only_events` exists under exactly that name and is green.
2. No `--due` argument (or any task-oriented flag) exists on `caldir new`; the second test proves it.
3. `new.rs` gains no `Todo` import, no `TodoStatus`, and no `CalendarItem::Todo` construction anywhere.
4. Any change to `new.rs` production code is **narrowing only** — the mechanical accessor adaptation the
   `CalendarItem` retype forces. No behavioural change, no new branch, no new flag.
5. `new`'s stdout text and exit codes are byte-identical to before this feature (C13).
6. Existing `new` tests pass **unmodified** (R104 — any required edit to an existing event test is a design
   failure, not a fixup).
7. `cargo test -p caldir-cli -- commands::new` green; full suite green.

## Non-goals

- Implementing task creation in any form. If it feels like a small addition, that is precisely the pressure
  R90 exists to resist; it needs an ADR first.
- A `caldir done` / `caldir complete` command.
- Touching `caldir-core`'s `Todo` constructors.

## Notes for the implementer

- **Trap — scope creep.** This ticket's entire value is the *absence* of a feature. If you find yourself
  reading RFC 5545's VTODO section, you have left the ticket.
- **Trap — asserting on prose.** Do not "pin" R90 with a comment. The clap-argument assertion is the guard;
  a comment is not.
- **Trap — the filename check.** `L1-07` reserves the `_task__` prefix. `new`'s slug comes from
  `Event::base_slug()` (`caldir-core/src/event/slugify.rs`), which C1 declares INVIOLABLE and `L1-07`
  explicitly does not touch — so assertion 3 should pass trivially. If it does not, you have found a C1
  breach and it must be reported, not worked around.
- Toolchain `1.97.0`; clippy `-D warnings`; CLI tests use `indoc`; never run two cargo commands in parallel.
