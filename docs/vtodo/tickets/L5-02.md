# L5-02 — component-aware UID lookup and `find_event_location` fast path

**Layer:** L5 (CalDAV provider) · **PR-2** · **Depends on:** `L5-01`

## Responsibility

Parameterise the UID-lookup REPORT's `comp-filter` by component kind, and make the `{uid}.ics`
fast path in `update_event` / `delete_event` component-aware, so a task update never targets an
event resource. The href stays `{uid}.ics` for **both** kinds.

## Requirements satisfied

- **R60** — *"The UID-lookup REPORT (`caldav/ops.rs:107`) MUST be component-parameterised. It has
  no time-range and needs only the component-name treatment."*
- **R61** — *"`find_event_location`'s fast path MUST also be component-aware: `update_event.rs:29`
  and `delete_event.rs:24` try `{uid}.ics` first and fall back to the hard-coded-VEVENT REPORT, so
  without this a task update or delete targets an event resource or fails to find its own."*
- **R62** — *"The href for a task MUST remain `{uid}.ics`, unchanged for both kinds. A kind-distinct
  href is unimplementable against the MVP's own target server: Radicale returns `409` +
  `<C:no-uid-conflict/>` for the same UID at a different href (probe Q-E.3). ADR-02 rule #4 is
  struck by ADJUDICATION C-1."*

## RED tests

`caldir-provider-caldav` gains **`wiremock = "0.6"` as a dev-dependency** (dev-only; nothing ships).
`create_caldav_client` accepts plain `http://` (`hyper_rustls … .https_or_http()`, `client.rs:38`),
so a wiremock server on `127.0.0.1` is a valid CalDAV base URL. `L5-03` and `L5-04` reuse it.

1. `caldav::ops::tests::find_event_location_is_component_aware_on_both_paths` **(T-39)**
   — in `caldir-provider-caldav/src/caldav/ops.rs`. Four sub-cases against a wiremock server:
   (a) `ComponentKind::Todo`, `{uid}.ics` holds a VTODO ⇒ fast path returns that href + etag;
   (b) `ComponentKind::Todo`, `{uid}.ics` holds a **VEVENT** ⇒ the fast path MUST NOT return it;
       the REPORT fallback runs and its captured body carries `<C:comp-filter name="VTODO">`;
   (c) `ComponentKind::Event`, `{uid}.ics` holds a VEVENT ⇒ byte-identical outcome to today
       (same href, same etag) — the R2/C2 no-regression half;
   (d) fast path 404 ⇒ REPORT fallback body carries the **requested** component name, and no
       `<C:time-range>` element (R60: the UID lookup has none, and never gains one).
   Why: without (b) a task PUT lands on an event resource and destroys it; without (c) this ticket
   silently changes event sync behaviour.

## Acceptance criteria

1. `find_event_location` takes the component kind as a parameter; `FindEventByUid` interpolates the
   component name into the filter at `ops.rs:107` instead of the literal `"VEVENT"`.
2. The UID-lookup REPORT body is otherwise **unchanged** — same `prop`, same `prop-filter name="UID"`,
   same `collation="i;octet"`, same `Depth: 1`, and still **no `<C:time-range>`**.
3. For `ComponentKind::Event`, the emitted REPORT body is byte-identical to today's.
4. The fast path resolves the kind of the resource at `{uid}.ics` before returning it, and falls
   through to the REPORT on a mismatch. Recommended implementation: replace the bare
   `GetEtag::new(&uid_href)` (`ops.rs:57`) with `GetCalendarResources::new(&calendar_href)
   .with_hrefs([&uid_href])` — the same request `create_event.rs:53` and `update_event.rs:52`
   already issue — then decode with `L5-01`'s `parse_item` (`caldav/ops.rs`) and compare kinds.
5. `update_event` and `delete_event` pass the kind of the item they are operating on. `delete_event`
   currently takes only `event_id: &str` (`delete_event.rs:18`) — it must receive the kind too;
   `caldir-core`'s `DeleteEvent` already carries the item after `L4-02`, so the kind is available at
   `commands/delete_event.rs` without a wire change (R52: **no new `Method` variant**).
6. The href construction (`event_url`, `client.rs:73-76`) is **unchanged**: `{calendar_url}/{uid}.ics`
   for both kinds. Do not add a suffix, a prefix, or a kind segment (R62).
7. `caldir-provider-icloud` compiles and its 14 tests pass with no source edits beyond what the
   `ops` signature change mechanically forces.

## Non-goals

- No 409 handling (that is `L5-03`) and no multi-component guard (that is `L5-04`).

- No change to the list REPORT (`ops/list_events.rs:103`) — that literal belongs to `L3-02`,

## Notes for the implementer

- `ComponentKind` may not be `pub` after `L1-06`. Exporting it from `caldir-core` is additive and
  permitted — `L8-04` bumps the minor version for the API break already.
- Radicale enforces UID uniqueness **per collection, component-type-agnostically** (probe Q-E), so
  in practice at most one resource per UID exists. The kind check is therefore not a lookup
  optimisation — it is the guard that turns "wrong kind at this href" into a clean not-found, which
  `L5-04` then surfaces as the R65 same-UID-pair push error instead of a destructive overwrite.
- Trap: `delete_event` treats *any* location-resolution failure as "already deleted" and returns
  `Ok(())` (`delete_event.rs:25-31`). After this change a kind mismatch reaches that branch. That is
  the correct outcome for delete (do not delete someone else's resource) — but do not widen the
  same swallow into `update_event`, which must error.
- Trap: `GetCalendarResources` returns `resources[].content` as a `Result`; today both call sites
  discard failures with `.ok()`. On the fast path a decode failure must mean "fall through", never
  "return this href anyway".
- Trap: `just check` runs clippy with `-D warnings`; never run two cargo commands in parallel.
