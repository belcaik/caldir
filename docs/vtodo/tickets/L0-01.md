# L0-01: incomplete-listing signal on `Calendar::events()`

**PR-1.** This ticket ships in the first PR together with `L0-02` and `L0-03`. R6 is explicit:
graceful per-file degradation ships first, as its own change, **and that change MUST include R48**
(`L0-03`). Landing L0-01/L0-02 without L0-03 is exactly the data-loss shape R48 exists to prevent.

**PR-1 turns NONE of the five VTODO RED tests green.** All five assert that a VTODO *loads and is
visible*; degrading softly is not the same thing. This ticket's exit criterion is its **own** new
test plus the unmodified 686-test baseline — never "the reproduction passes".

## Responsibility
`Calendar::events()` stops `?`-aborting the whole calendar listing when one `.ics` file fails to
load. It returns the successfully loaded `CalendarEvent`s **plus a record of the files it skipped**,
so downstream code can tell a complete listing from an incomplete one. This settles Q-6 by changing
the return type to a small listing struct.

## Requirements satisfied
- **R6** (part) — *"Levels 2 and 3 are a pre-existing defect independent of VTODO modelling. Graceful per-file degradation SHOULD ship first, as its own change, and that change MUST include R48 — without it, a degrading core paired with a VTODO-aware provider deletes the user's tasks server-side."*
- **R78** — *"`Calendar::events()` MUST NOT return a silently-short `Ok(vec)`: either it errors, or it returns the loaded items **plus a signal that the listing is incomplete** — the signal R48 consumes."*
- **R74** (mode-A half) — *"Both MUST be fixed, and the fix for A MUST NOT introduce B. A is fixed by per-file graceful degradation plus R48; B by R19 (loud on unknown) and R49 (never infer a delete from a task-less response)."*
- **R5** (level 2) — *"A file containing exactly one VTODO MUST load, MUST NOT error, and MUST NOT prevent any sibling file, sibling calendar, or CLI aggregation from loading."* (This ticket delivers only the *sibling file does not die* half; the VTODO still fails to load until `L2-06`/`L2-07`.)

## RED tests
This ticket adds **one** new test; it turns no existing RED test green.

- **ADD** `calendar::tests::an_unreadable_file_is_skipped_and_reported_not_fatal`
  in `caldir-core/src/calendar.rs`'s `#[cfg(test)] mod tests`.
  It MUST write two files into a `test_calendar()`: one good VEVENT (`test_utils::VEVENT_CONTROL_ICS`
  via `test_utils::write_ics`) and one deliberately broken `.ics`, then assert:
  1. the call returns `Ok` (not `Err`) — proves the per-file `?` escalation at `calendar.rs:114` is gone;

## Acceptance criteria
1. `Calendar::events()` no longer propagates a per-file load error; a directory-level error (e.g.
   `read_dir` failure) still returns `Err`. (R78)
2. The return type carries both the loaded events and the skipped-file records, and exposes a
   predicate an incomplete listing can be recognised by (consumed by `L0-03`). (R78, Q-6)
3. `calendar::tests::an_unreadable_file_is_skipped_and_reported_not_fatal` passes. (R5 level 2, R78)
4. The whole workspace compiles and `just test` shows the unmodified 686-test baseline green, with
   **zero edits to existing event tests**. (R104)
5. No file is dropped from the listing silently: skipped count + loaded count == `.ics` files seen.

## Notes for the implementer
- Keep the outer `Result`. `Calendar::events() -> Result<CalendarListing, CalendarError>` lets every
  `self.events()?` call site keep its `?` and only adapt what it does with the value. Anything that
  drops the `Result` multiplies call-site churn far beyond Q-6's estimate.
- **Compile-scope trap — INDEX under-lists the files.** The retype reaches
  `caldir-core/src/connection.rs:38, 68, 98, 125` and `caldir-cli/src/commands/rsvp.rs:91`, neither
  of which is in this ticket's file list. Make the *minimal mechanical* adaptation there
  (e.g. `.events()?.into_events()`); change no behaviour in those files. Report the extra files in
  your handoff.
- **Immutable-test trap.** `calendar::tests::events_lists_a_vtodo_file_alongside_its_vevent_sibling`
  (`calendar.rs:1161`) and `caldir::tests::vevent_calendar_lists_independently_of_a_sibling_vtodo_calendar`
  (`caldir.rs:417`) call `calendar.events()` and will not compile after the retype. The ADJUDICATION
  post-DAG ruling applies: **accessors may be adapted, assertions may not.** Every adaptation must
  read in the diff as a mechanical rename with the assertion line untouched; the test names must not
  change. `events_lists_a_vtodo_file_alongside_its_vevent_sibling` MUST still fail after this ticket
  (it now fails on the missing VTODO, not on the aborted listing) — do not "fix" it.
- The skipped record needs the path and the error; `L0-02` renders the error string as
  `DoctorWarning::UnreadableEvents` and `L0-03` only needs "is it non-empty".
- Follow the crate's test conventions: inline `#[cfg(test)] mod tests`, no fixture files,
  `use pretty_assertions::assert_eq;`, bind the `TempDir` (`let (_tmp, calendar) = ...`).
- CI runs `just check` with `RUSTFLAGS: -D warnings` and `just test` under `TZ` =
  `UTC` / `Europe/Stockholm` / `America/New_York`. Nothing here should be zone-sensitive; if it is,
  you have introduced a bug.
