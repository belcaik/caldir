# L4-02 — RPC method structs carry an item; **no new `Method` variant**

> Layer L4 · PR-2. Four files under `caldir-core/src/rpc/methods/`.

## Responsibility

Retype the typed payload fields on `CreateEvent`, `UpdateEvent`, `DeleteEvent` and the
`ListEvents` **response** to `CalendarItem`. The JSON on the wire stays a **string**.

Three constraints govern every line of this ticket:

- `Method` gains **no variant, ever**.
- Every added field is **additive and `Option`-typed**.
- `#[serde(deny_unknown_fields)]` appears **nowhere**.

## Requirements satisfied

- **R52 (INVIOLABLE).** *"`Method` MUST gain no variant — no `list_todos`, no `create_todo`. It
  is a closed serde enum with no `#[serde(other)]` (`rpc/methods.rs:22-31`), so a new verb
  hard-breaks every installed provider binary mid-upgrade. Component kind travels **inside the
  opaque ICS payload**."* Mirrored as **C8 (INVIOLABLE)**.
- **R53.** *"The RPC method structs carry a **typed** item, not opaque text
  (`rpc/methods/delete_event.rs:6-10` is `pub event: Event` with
  `#[serde(with = "crate::rpc::ics")]`; `ListEvents`'s response is `Vec<Event>`). Those typed
  fields MUST become item-typed or a task can be neither created, updated, nor deleted. The JSON
  on the wire stays a string, so R52/R55 are unaffected."*
- **R55 (INVIOLABLE).** *"RPC fields MUST be additive and `Option`-typed;
  `deny_unknown_fields` MUST NOT appear anywhere."* Mirrored as **C9 (INVIOLABLE)**.

## Dependencies

`L4-01` (the item-typed `rpc::ics` codec).

## RED tests

**`T-33`** — `rpc::tests::method_set_is_exactly_the_six_known_verbs`.
Asserts the serialized names are exactly `connect`, `list_calendars`, `list_events`,
`create_event`, `update_event`, `delete_event` — no more, no fewer. *Why:* R52/C8. This is a
**tripwire**: it must fail the day anyone adds `create_todo`, which is the single change that
hard-breaks every installed provider binary mid-upgrade.

**`T-34`** — two tests:
`rpc::tests::request_structs_ignore_unknown_fields` — deserialize each request struct from JSON
carrying an extra unknown key and assert it succeeds; and
`rpc::tests::deny_unknown_fields_appears_nowhere` — a source-level assertion that the literal
`deny_unknown_fields` does not occur under `caldir-core/src/rpc/`. *Why:* R55/C9 — a future
"tightening" of one struct silently breaks forward compatibility with newer providers.

**`T-36`** — `rpc::methods::tests::create_update_and_delete_carry_a_task_payload`.
**REFUSED, and the name is unwritable (ADJUDICATION; recorded in `spec.md` §18).** R70 keeps the
outbound field `pub event: Event` on all three structs, so no task payload can ride them by
construction; the ticket text below describes a document that cannot be built. `L4-02` shipped the
honest counterpart instead — `rpc::tests::a_task_payload_is_rejected_by_every_outbound_request_struct`
— which asserts the attempt aborts loudly with `expected 1 event(s) in ICS, found 0` on all three.
The original text is kept verbatim below as the record of what was asked.
Builds each of the three commands with a **task** payload, calls `to_json()`, and asserts:
`json["command"]` is the existing verb; `json["params"]["event"]` is a **string** starting
`BEGIN:VCALENDAR` and containing `BEGIN:VTODO`; and it contains **no** `BEGIN:VEVENT`. *Why:*
R53 + R1 — the kind must travel inside the opaque payload and nowhere else.

Place `T-33`/`T-34` in `caldir-core/src/rpc.rs`'s (or `methods.rs`'s) test module per the paths
above; `T-36` in the methods test module. Existing `*_serializes_json` tests stay green.

## Acceptance criteria

1. `Method` has exactly six variants, unchanged names, no `#[serde(other)]`, no new variant.
2. `CreateEvent.event`, `UpdateEvent.event`, `DeleteEvent.event` and `ListEvents`'s
   `type Response` are item-typed; the field **names** are unchanged.
3. `ListEvents`'s response is still a bare `Vec<…>` — **not** wrapped in an object.
4. Any new field added anywhere under `rpc/` is `Option`-typed with a serde default and is
   omitted when `None`.
5. `deny_unknown_fields` occurs nowhere in the workspace's RPC modules.
6. The on-wire JSON for an **event** payload is byte-identical to today (the migration
   guarantee: existing providers see no change at all).
7. `T-33`, `T-34` (both names), `T-36` exist and pass.
8. `cargo test --workspace --no-fail-fast` green — every provider crate deserializes these.

## Non-goals

- Any new verb, any capability field, any negotiation handshake. ADR-07 was **cut entirely**
  from the MVP (ADJUDICATION); R49's data-only belt (`L3-04`) is what replaces it.
- Renaming the `Event*`-prefixed shared types (R94, deferred; recorded by `L8-06`).
- `Connection` apply loops — `L4-03`.
- Provider-crate behaviour. `L2-05` already made them compile; R70/R73 forbid behaviour edits.

## Notes for the implementer

- **Trap — the "obvious" API.** A `create_todo` verb reads as the clean design and is exactly
  what R52 forbids: `Method` is a closed serde enum with **no `#[serde(other)]`**, so an
  installed older provider binary fails to deserialize the request outright. There is no
  deprecation path. `T-33` is the tripwire; do not weaken it to a `>=` check.
- **Trap — `#[serde(flatten)]` and unknown fields.** `flatten` interacts badly with
  `deny_unknown_fields`; that is one more reason it must appear nowhere (R55). Do not "fix" a
  flatten warning by adding it.
- **Trap — old core + new provider is only safe because decode is loud** (R57). Nothing in this
  ticket may make a decode failure recoverable, defaulted, or skipped.
- `field name` stability matters more than type stability here: the wire sees `"event"` as a
  string either way, so renaming the field to `"item"` would be a gratuitous break. Keep it.
- `MockProvider::captured_request::<C>()` asserts `request.method == C::METHOD`
  (`mock_provider.rs:46`) — tests that decode a captured request are also verb assertions.
