# L6-01 — pin the accepted Google/Outlook/webcal consequences; ship no capability mechanism

**Layer:** L6 (unsupported-provider behaviour) · **PR-2** · **Depends on:** `L4-03`, `L3-04`

## Responsibility

Lock the **ADR-07 cut** in tests and prose. Pushing a task to a Google- or Outlook-backed calendar
aborts the rest of that calendar's push with `expected 1 event(s) in ICS, found 0` — ugly,
recurring, and **not data loss**. This ticket turns that from an accident into a *tested, known,
documented* behaviour. A webcal VTODO-only feed returning zero tasks must not delete local tasks.
**Nothing else ships**: no config field, no builder, no provider-crate edit, no third diff bucket,
no warning renderer.

## RED tests

Both live in `caldir-core/src/connection.rs`'s `#[cfg(test)] mod tests`. Layer **C**.

> **CORRECTION (ADJUDICATION) — the provider-error-envelope path below is UNREACHABLE and was
> correctly refused.** Under R70 the outbound RPC field stays `Event`, so core aborts inside
> `into_event()` **before** any RPC is serialized. An old provider binary never receives the
> `BEGIN:VTODO` payload and therefore never emits that envelope. Injecting one would test a
> fabricated path *and* assert that a request reached the wire, contradicting the locked
> `!mock.received_a_request()`. The shipped test drives the abort from **core**, not from an
> injected envelope, and still pins the byte-exact literal
> `expected 1 event(s) in ICS, found 0` (`event/error.rs`, `UnexpectedEventCount`) — only its
> *source* changes. (The sibling lock on the **inbound** decode is a different literal:
> `expected 1 supported component(s) in ICS, found {n}`, `EventError::UnexpectedComponentCount`.)
> AC 6 (`reply_provider_error`) is **struck** for the same reason; no such helper ships.

1. `connection::tests::pushing_a_task_to_a_task_less_provider_fails_that_calendar_without_data_loss`
   **(T-50 — shared with `L4-03`; this ticket adds the pinned message and the no-data-loss half.)**
   ~~A writable connection whose provider answers the `CreateEvent` with an **error response**
   (`{"status":"error","error":"expected 1 event(s) in ICS, found 0"}` — the shape an old, still-
   `Event`-typed provider binary emits when its `rpc::ics` decoder meets a `BEGIN:VTODO` payload).~~
   Assert, in order:
   (a) `apply_outgoing_diff` returns `Err`;
   (b) the error string **contains** `expected 1 event(s) in ICS, found 0` — the literal from
       `event/error.rs:11`, which is the whole point of R71;
   (c) a *second* outgoing change queued after the failing one produced **no** RPC — the abort at
       `connection.rs:231` really does stop the rest of that calendar's push;
   (d) every local `.ics` file is byte-identical to before, and `known_event_ids` / `bases/` gained
       no entry for the failed item.
   Why: (b) makes the ugly message a contract instead of an accident; (c)+(d) are what "**not** data
   loss" means and are the only reason the ADR-07 cut was acceptable.
2. `connection::tests::a_task_less_feed_does_not_delete_local_tasks` **(new)**
   The webcal shape: a local calendar holding ≥1 task **with a known base**, plus at least one
   event, and a `ListEvents` reply containing events but **zero** tasks. Assert the resulting diff
   contains **no** incoming `Delete` for any task, and that the event side is diffed exactly as it
   would be today. Why: `caldir-provider-webcal/src/commands/list_events.rs:16-25` silently drops
   VTODOs from a feed, so absence there means "provider cannot see tasks", never "the user deleted
   them". This is R49's belt observed from the `Connection` seam rather than from
   `CalendarDiff::compute` (where `L3-04`'s `T-30` already pins it).

## Non-goals

- **Do not** make the Google/Outlook error message nicer, shorter, or task-aware. That is precisely
  what ADR-07 bought and precisely what was cut. A prettier message here re-opens the decision.
- **Do not** filter tasks out of the outgoing set for VEVENT-only providers "to be helpful" — that
  would be the capability mechanism wearing a disguise, and it silently stops syncing user data.
- **Do not** implement `supported-calendar-component-set` (R92 — record only; it is advisory and a
  VEVENT PUT into a VTODO-only collection returned `201`, so it can never be an enforcement point).
- No Google Tasks / Microsoft To Do API work (R86 — new OAuth scopes, re-consent for every user).
- No webcal VTODO parsing (R72).

## Notes for the implementer

- **The abort point is `connection.rs:231`**, the `?` on `remote.apply_change(change).await?` inside
  `push_outgoing_changes`. `diff.outgoing()` is iterated in order, so the failure kills every change
  after it too — that is the "aborts the rest of that calendar's push" clause, and criterion 1(c) is
  what proves it rather than assuming it.
- **Where the message comes from.** `EventError::UnexpectedEventCount` (`event/error.rs:11`) is
  raised by an `Event`-typed `rpc::ics` decoder meeting a `BEGIN:VTODO` document — i.e. by an
  **installed, older provider binary**, since providers ship and upgrade separately from core
  (`CLAUDE.md` §Architecture). Do not try to raise it from inside core; inject it as a provider
  error response, which is exactly what the subprocess transport would deliver.
- Other calendars are unaffected: the abort is scoped to one `Connection`. Say so in the website
  note, because "sync broke" reads worse than it is.
- Trap: `MockTransport::exchange` **panics** when its FIFO response queue is empty
  (`mock_transport.rs:82`), so queue exactly as many replies as RPCs you expect — and in test 1(c)
  queue *nothing* for the second change, so an unexpected second RPC panics loudly instead of
  silently passing.
- Trap: bind the `TempDir` returned by `test_caldir()` (`let (_tmp, …)`) or the calendar directory is
  deleted mid-test (`docs/vtodo/context/testing.md` §2).
- Trap: `just check` runs clippy with `-D warnings`; never run two cargo commands in parallel
  (`rust-toolchain.toml` pins `1.97.0` and parallel invocations race rustup).
