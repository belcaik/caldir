# L4-03 — `Connection` pushes/pulls items end to end

> Layer L4 · PR-2. `Connection` is the **highest no-network seam** in the workspace: everything
> real except the transport (`docs/vtodo/context/testing.md` §5).

## Responsibility

Carry items through the apply loops. A task push reaches `CreateEvent` as a `BEGIN:VTODO`
payload and **never** as a VEVENT. Pin the two accepted skew failures as *failures*, not as
silent successes:

- **new core + old provider** (R56): the push fails that calendar and stops — ugly, not data loss;
- **old-shaped list from a newer provider** (R57): the whole list fails **before any apply**.

## Requirements satisfied

- **R1 (INVIOLABLE, end-to-end).** No VEVENT is created anywhere in the chain for a task
  (spec §17 A-1 item 3).
- **R56.** *"New core + old provider MUST be safe. Stated precisely … pushing a task to a
  provider that cannot represent one produces a decode failure whose `?` at
  `caldir-core/src/connection.rs:231` **aborts the rest of that calendar's push**. Ugly and
  recurring; **not data loss** — R48 and R49 cover the destructive variants."*
- **R57 (INVIOLABLE).** *"Old core + new provider MUST be safe *because* R19 holds: a VTODO
  payload fails the old `Vec<Event>` deserialization, one bad element fails the whole vector,
  the call errors, and the sync aborts **before any apply**."*
- **R71** (unsupported-provider behaviour at the connection tier; spec §13).
- **R100 (A-6), end-to-end.** *"A directory holding a VEVENT file and a VTODO file sharing a UID
  MUST produce two identities, two base entries, two `known_event_ids` lines, two base files …
  and … exactly **one** delete against the correct file."*

`L4-02` (item-typed method structs), `L3-03` (kind-aware diff).

## RED tests

All in `caldir-core/src/connection.rs`'s inline `#[cfg(test)] mod tests`, layer **C**, built on
`writable_connection()` (`connection.rs:278`).

**`T-48`** — `connection::tests::a_task_is_pushed_as_a_vtodo_and_never_as_a_vevent`.
Asserts the captured `CreateEvent` payload **contains `BEGIN:VTODO`** and **contains no
`BEGIN:VEVENT`**. *Why:* R1/A-1 item 3 — the one assertion that proves the kind survived the
whole chain rather than being flattened to an event somewhere in the middle.

**`T-50`** — `connection::tests::pushing_a_task_to_a_task_less_provider_fails_that_calendar_without_data_loss`.
Queue a provider error/decode failure for the task push. Asserts: `apply_outgoing_diff` returns
`Err`; **the local file still exists and is unmodified**; no delete was applied. *Why:* R56 —
the accepted failure is "ugly", and this test is what keeps it from becoming "destructive".

**`T-51`** — `connection::tests::a_task_payload_from_a_newer_provider_fails_the_whole_list_before_any_apply`.
Queue a `ListEvents` response whose vector contains one decodable item and one undecodable
payload. Asserts the call errors and **nothing was applied** — no file created, updated or
deleted, no base recorded. *Why:* R57 INVIOLABLE. The catastrophic alternative is a silent drop,
which makes the remote list arrive short and feeds the delete path.

**`T-52`** — `connection::tests::a_mixed_local_directory_keeps_both_items_distinct_end_to_end`.
A calendar holding a VEVENT and a VTODO sharing one UID. Asserts two identities, two base
files, two `known_event_ids` lines, and — both present locally, neither remote, the shared id
known — exactly **one** delete against the correct file. *Why:* A-6/R100.

## Acceptance criteria

1. `Connection::diff`, both apply loops and `discard_outgoing_diff` all carry items; the
   `HashMap<EventInstanceId, CalendarEvent>` keys are kind-carrying.
2. A task `Create` reaches the transport as `rpc::CreateEvent` (the **existing** verb) with a
   `BEGIN:VTODO` payload; no VEVENT appears in any captured request for a task.
3. `bases_to_backfill` (`:162`) compares like against like: a task is never judged "in sync"
   against an event.
4. A push failure mid-loop still flushes the bases recorded so far — the existing
   `loop_result` / `record_result` ordering at `:114-118` and `:84-88` is preserved.
5. A `ListEvents` decode failure aborts **before** any file is written, deleted or updated.
6. `T-48`, `T-50`, `T-51`, `T-52` exist with exactly those names and pass.
7. `SUITE` green with zero edits to existing event tests (R104).

## Non-goals

- The A-2 idempotence gate — `L4-04` (`T-49`).
- Webcal / task-less-feed behaviour — `L6-01` (shares `T-50`'s shape, adds its own case).
- Any capability probe or provider allow-list. ADR-07 is **cut**; the failure above is accepted.
- Any raw-byte comparison as an assertion (R30) — see `L4-04`.

## Notes for the implementer

- **`T-52` fixture constraint — binding, from the reconciliation pass.** `L5-04` makes a local
  same-UID event/task pair targeting **one** collection a **push error** (R65/R80, INVIOLABLE). Do
  **not** write `T-52` so that both items are pushed into one remote collection: `L5-04` will turn
  it red, and the correct resolution is a fixture change here, **not** a weakened guard there.
  A-6/R100 asks for *distinct identities and one correct delete*, never a successful dual push.
  Prove distinctness with two identities, two `bases/` files, two `known_event_ids` lines and
  exactly one delete against the correct file; either keep the pair out of a same-direction push,
  or split it across two remotes. Any assertion of the form "both creates succeeded against one
  collection" belongs to `L5-04` as an **error**-path case, with the live proof in `T-56`. Mirror
  note in `L5-04.md`.
- **Trap — `MockTransport` panics on an empty queue** (`mock_transport.rs:82`). Every RPC the
  code makes needs exactly one `reply()`, in order. If a test panics with "no queued response",
  the production path made an **extra** call — investigate before adding another `reply()`.
- **Trap — `captured_request()` returns the *last* request** (`:56`). For a multi-change diff,
  asserting on it silently tests only the final call. `T-48` should push exactly one change.
- **Trap — `push_outgoing_changes` mutates local files from the provider's echo** (`:242-246`):
  the returned item is written back over the local file. If a provider echoes a VEVENT for a
  task, that write is the data loss. `T-48`'s "never a VEVENT" assertion is the upstream guard.
- **Trap — `unreachable!("apply_change returns None for Delete")` at `:239`.** Keep that
  invariant true for tasks, or a task delete panics in production.
- Bind the `TempDir` (`let (_tmp, ...)`) or the calendar is deleted mid-test.
- `test_utils.rs` is crate-private to `caldir-core` — these tests are the reason the whole tier
  lives in-crate.
