# L3-02 — the window rule (R44) + the bare comp-filter (R51/R58) 🔒 ONE COMMIT

> Layer L3 · PR-2 · **the single most dangerous ticket in this effort.**
> Four files across two crates. **It may not be split** (INDEX §5, spec §10 and §12).

## 🔒 Hard constraint: R44, R51 and R58 ship in ONE commit

The spec states it twice. §10: *"**D1 (the window rule, R44) and D2 (no time-range on the VTODO
query, R51/R58) are ONE decision and MUST ship in ONE commit.** D2 alone is merely inefficient.
**D1 alone CREATES the bug**: D1 is what makes an undated task in-window and therefore
deletable, while a time-ranged query is what makes it absent. Neither half is safe without the
other."* §12 restates it: *"Shipping R58 alone is merely inefficient; shipping R44 alone
*creates* the deletion bug."*

**The bug R44-alone creates, traced in real code:** the server omits a previously-synced
completed task → `remote_by_id` (`calendar_diff.rs:25`) has no entry → pass 1 falls through to
the window check → the task is undated and therefore in-window, so it is **not** skipped →
`sync_bases.get(&id).is_some()` is true → an `incoming Delete` **removes the user's file**.
`allow_mass_delete` (`caldir-cli/src/utils/guards.rs:10`) counts only *outgoing* deletes, so it
never fires. Silent, needs no server bug, and it targets the user's archive.

A reviewer who asks for this ticket to be split must be shown spec §10.

## The citation and the live evidence

**RFC 4791 §9.9** defines time-range matching for VTODO over
`DTSTART`/`DURATION`/`DUE`/`COMPLETED`/`CREATED`. The row `DTSTART=N, DUE=N, COMPLETED=Y,
CREATED=N` matches only when `start <= COMPLETED AND end >= COMPLETED`. A VTODO whose **only**
date property is a `COMPLETED` older than the window start therefore evaluates FALSE and a
compliant server **MUST NOT return it**.

**Confirmed live against Radicale 3.7.6** (`docs/vtodo/context/radicale-probe.md` Q-B, 8
fixtures, all six §9.9 rows matched): fixture `t2` (`STATUS:COMPLETED` +
`COMPLETED:20200101T000000Z`, **no DTSTART, no DUE**) is **OMITTED** by a `calendar-query`
carrying `<C:time-range start="20250825T000000Z" end="20270825T000000Z"/>` and **returned** by
the same query without it; fixture `t1` (fully undated) is **RETURNED by both**; `DTSTAMP` does
not participate; fixture `t5` (`CREATED` only) is rescued by the `end > CREATED` row — why
`CREATED` is modelled (R13, C-4), **defence in depth, never a substitute for R58**.

## Responsibility

**(a) Core:** replace the window check at `calendar_diff.rs:78-90` with a component-aware
predicate — for tasks, the *"core's rule"* column of §9.9 with `start = from`, `end = to`.
**(b) Provider:** emit `<C:comp-filter name="VTODO"/>` **bare**, no `<C:time-range>` child, as a
**separate REPORT** from the existing VEVENT + time-range query. Both in the same commit.

## Requirements satisfied

- **R44 (INVIOLABLE, ships with R51/R58).** *"The in-window predicate for tasks MUST be the
  'core's rule' column of §9.9, with `start = from`, `end = to`"*:

  | DTSTART | DUE | core's rule |
  |---|---|---|
  | Y | Y | `(from < DUE OR from <= DTSTART) AND (to > DTSTART OR to >= DUE)` |
  | Y | N | `from <= DTSTART AND to > DTSTART` |
  | N | Y | `from < DUE AND to >= DUE` |
  | N | N | **TRUE, unconditionally** |

  *"`COMPLETED` and `CREATED` MUST NOT be consulted by core: core must be *more* permissive
  than any server, never less."*
- **R45.** *"The event predicate `occurs_in_range` (`event.rs:136-141`) MUST be unchanged, byte
  for byte (R2)."*
- **R46 (INVIOLABLE).** *"No synthesized dates. An undated task MUST NOT be given a fabricated
  `DTSTART` (epoch, `COMPLETED`, 'now') … an epoch start evaluates false at
  `calendar_diff.rs:80` and would silently make undated tasks **unpushable** at `:89`."*
- **R47.** *"Polarity, because it is easy to state backwards: `in_range == false` → `continue` →
  **no delete and no create**; `in_range == true` *authorizes* deletion."*
- **R51 (INVIOLABLE, ships with R44).** *"The CalDAV VTODO `calendar-query` MUST carry **no**
  `<C:time-range>`."*
- **R58 (INVIOLABLE, ships with R44).** *"The VTODO `calendar-query` REPORT MUST be emitted as a
  **bare comp-filter** — `<C:comp-filter name="VTODO"/>` — with **no `<C:time-range>` child**."*
- **R59.** *"The VTODO query MUST be a **separate REPORT** … §9.7.1 says a comp-filter matches
  when its children '**all** match', i.e. siblings read as AND, which would match nothing."*
- **R97 (INVIOLABLE, A-3).** *"a previously-synced undated task whose only date property is a
  `COMPLETED` older than the window start … MUST leave the file in place and produce no incoming
  delete for it. Prevented by R44 and R58 **together**."*
- **R98 (A-4).** *"An undated local task with no base MUST produce exactly one outgoing create
  against a bounded window — never a skip (R46, R47)."*

table, before touching the predicate** (INDEX §6 risk 2). Asserts each of the four rows at

**`T-25`** — `diff::calendar_diff::tests::an_undated_task_with_a_known_base_and_an_empty_remote_is_not_deleted`.
Asserts `incoming.is_empty() && outgoing.is_empty()` for an undated local task with a known base
against an **empty** remote list and a bounded range. *Why:* A-3 / R97 — the exact shape of the
data-loss bug.

**`T-26`** — `diff::calendar_diff::tests::an_undated_task_with_no_base_produces_one_outgoing_create`.
Asserts **exactly one** `EventChange::Create` in `outgoing`, empty `incoming`. *Why:* A-4 / R98,

**`T-37`** — `caldav::ops::list_events::tests::the_vtodo_report_body_contains_no_time_range`
in `caldir-provider-caldav/src/caldav/ops/list_events.rs`. Asserts the VTODO REPORT body contains
`comp-filter name="VTODO"` and **not the substring `time-range`**. Spec T-37 requires *"a
**named** assertion whose comment cites RFC 4791 §9.9 and this spec's §10/§12"* — put that
citation in the assertion message.

**`T-38`** — `caldav::ops::list_events::tests::the_vtodo_report_is_a_separate_request_from_the_vevent_report`.
Asserts two distinct request bodies are produced — one VEVENT body that still carries its
`<C:time-range>`, one VTODO body that does not — and that neither is a sibling comp-filter
inside the other (R59).

## Acceptance criteria

1. A task's in-window predicate implements the R44 table **exactly**, including `N/N ⇒ TRUE`.
2. `COMPLETED` and `CREATED` are **not read** by the predicate. Grep the predicate body: neither
   identifier appears.
3. No synthesized date anywhere on the task path (R46). No `unwrap_or(epoch)`, no
   `due.or(completed)`, no `Utc::now()` fallback.
4. `Event::occurs_in_range` (`event.rs:136-141`) and `has_occurrence_in_range` are **unchanged**
   — `git diff` shows zero lines touched in that range (R45, C2).
5. Polarity holds: for a task where the predicate is `false`, the loop `continue`s and emits
   **neither** a delete **nor** a create (R47).
6. The CalDAV VTODO REPORT body contains no `time-range` substring (R51, R58).
7. The VTODO REPORT is issued as a **second, separate** REPORT; the VEVENT REPORT body is
   **byte-identical to today**, time-range included (R59, zero VEVENT regression).
8. `T-24`, `T-25`, `T-26`, `T-37`, `T-38` exist with exactly the names above and pass.
9. `T-24` passes under `TZ=UTC`, `TZ=Europe/Stockholm` **and** `TZ=America/New_York`.
10. The whole change is **one commit** (see the hard constraint above).
11. `SUITE` green, zero edits to existing event tests (R104).

## Notes for the implementer

- **Trap 1 — the polarity. R47 exists solely because this is easy to state backwards.** At
  `calendar_diff.rs:78-90`: `in_range == false` ⇒ `continue` ⇒ **no delete AND no create**;
  `in_range == true` is the branch that **authorizes deletion** (`sync_bases.get(&id).is_some()`
  ⇒ `incoming Delete`). Backwards still compiles and still passes a careless test. `T-25`/`T-26`
  pin the two halves separately for exactly this reason.
- **Trap 2 — the tempting reuse.** Giving an undated task a fake `DTSTART` to reuse
  `occurs_in_range` looks harmless and is forbidden by R46: an epoch start evaluates **false**,
  the task is then never in-window, and it becomes silently **unpushable** — no create is ever
  emitted at `:89`. The failure is invisible; nothing errors.
- **Trap 3 — the "optimization" that reintroduces the bug.** Re-adding `<C:time-range>` to the
  VTODO query is the likeliest future regression (spec calls R58 *"the requirement most likely to
  be 'optimized' back into a bug"*). `T-37` is the lock; keep the RFC citation in its message.
- **Trap 4 — sibling comp-filters.** Never put `VEVENT` and `VTODO` comp-filters side by side
  under one `VCALENDAR` filter: §9.7.1's children-all-match wording reads as AND and would match
  nothing, and whether Radicale ORs siblings is **UNVERIFIED** (R59). Two REPORTs.
- The request body is built inside `prepare_request` (`list_events.rs:93`), which is private and
  needs a `Uri`. To make `T-37`/`T-38` testable without a network or a client, extract body
  construction into a small pure function returning `String` and call it from both
  `prepare_request` and the tests. Do not add a test-only HTTP client.
- `fetch_events` currently drops unparseable resources silently (`list_events.rs:37-41`,
  `parse_event` at `ops.rs:32`). That is `L5-01`'s ticket (R66) — **do not fix it here**, and do
  not let the second REPORT's results ride a path that hides it further.
- `test_utils.rs` is crate-private to `caldir-core`; caldav tests build their own fixtures.
