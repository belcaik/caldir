## The `Todo` type

```rust
// src/components/todo.rs:5-9
/// VTODO  [(RFC 5545, Section 3.6.2 )](https://tools.ietf.org/html/rfc5545#section-3.6.2)
#[derive(Debug, Default, PartialEq, Eq, Clone)]
pub struct Todo {
    pub(super) inner: InnerComponent,
}
```

`InnerComponent` (`src/components.rs:25-30`) is `pub(crate)`:

```rust
pub(crate) struct InnerComponent {
    pub properties: BTreeMap<String, Property>,
    pub multi_properties: BTreeMap<String, Vec<Property>>,
    pub components: Vec<Other>,
}
```

Two consequences that matter: single-valued properties live in a **`BTreeMap` keyed by property
name** (so a repeated property overwrites, and output is alphabetically ordered), and child
components are untyped `Other`.

### Inherent methods on `Todo` (the complete list)

Every one of these is in `src/components/todo.rs`:

`mark_uncompleted` removes `COMPLETED` and `PERCENT-COMPLETE` unconditionally, and removes `STATUS`
only when it currently equals `COMPLETED` (`src/components/todo.rs:129-139`).

`percent_complete` takes `u8` and does **no** range check — `percent_complete(200)` writes
`PERCENT-COMPLETE:200`. `get_percent_complete` is `self.property_value(..)?.parse().ok()`, so a
stored `200` parses back fine but a stored `999` yields `None` (u8 overflow).

`completed()` only accepts `DateTime<Utc>`; `get_completed` goes through `parse_utc_date_time`, so a
non-UTC `COMPLETED` value read from a file returns `None` (verified, see probe 9 below).

## Parsing

`Calendar` is the only entry point for a full file:


The error type is `String` (a pretty-printed nom `VerboseError`), not a structured error.

Component dispatch — this is where `VTODO` becomes a `Todo`:

```rust
// src/parser/components.rs:160-170
impl<'a> From<Component<'a>> for CalendarComponent {
    fn from(component: Component<'a>) -> CalendarComponent {
        use crate::{Event, Todo, Venue};

            "VEVENT" => Event::from(InnerComponent::from(component)).into(),
            "VTODO" => Todo::from(InnerComponent::from(component)).into(),
```

`impl FromStr for CalendarComponent` (`src/parser/components.rs:172-179`) parses a single bare
component (verified: `BEGIN:VTODO…END:VTODO` with no `VCALENDAR` wrapper works).

### Multi-value properties

Which keys land in `multi_properties` is a hard-coded list — this is the single most important
parsing fact for VTODO round-tripping:

```rust
// src/parser/properties.rs:27-44
/// [RFC-5545] states that the following "MAY occur more than once" in a VEVENT, VTODO, ...
const MULTIS: [&str; 13] = [
    "ATTACH", "ATTENDEE", "CATEGORIES", "COMMENT", "CONTACT", "EXDATE",
    "FREEBUSY", "IANA-PROP", "RDATE", "RELATED", "RESOURCES", "RSTATUS", "X-PROP",
];
```

`"RELATED"`, `"RSTATUS"`, `"IANA-PROP"` and `"X-PROP"` are **ABNF placeholder names from RFC 5545,
not real property names**. The real properties are `RELATED-TO` and `REQUEST-STATUS`; `IANA-PROP` /
`X-PROP` stand for "any IANA-registered or X- property". So in practice only 8 of the 13 entries ever
match a real line, and repeated `RELATED-TO`, `REQUEST-STATUS` or repeated `X-*` properties are
silently collapsed to the last occurrence.

### Value unescaping

`src/parser/properties.rs:424-431` calls `unescape_by_value_type` using
`determin_value_type(name, params)` (`:377-384`), which resolves `VALUE=` first, else
`ValueType::by_name` (`src/value_types.rs:39-100` — a hard-coded RFC table that includes
`PERCENT-COMPLETE`, `PRIORITY`, `STATUS`, `COMPLETED`, `DUE`, `RELATED-TO`, …). Only `ValueType::Text`
is unescaped (`src/parser/parsed_string.rs:31-56`, unescaping `\\ \, \; \: \N \n`). **Unknown `X-*`
properties resolve to `None` and are therefore never unescaped, and never escaped on write.**

## Serialization

One function does all of it (`src/components.rs:96-122`, the `Component::fmt_write` default method):

```rust
fn fmt_write<W: fmt::Write>(&self, out: &mut W) -> Result<(), fmt::Error> {
    write_crlf!(out, "BEGIN:{}", self.component_kind())?;
    if !self.properties().contains_key("DTSTAMP") {
        let now = Utc::now();
        write_crlf!(out, "DTSTAMP:{}", format_utc_date_time(now))?;
    }
    for property in self.properties().values() { property.fmt_write(out)?; }
    if !self.properties().contains_key("UID") {
        write_crlf!(out, "UID:{}", Uuid::new_v4())?;
    }
    for property in self.multi_properties().values().flatten() { property.fmt_write(out)?; }
    for component in self.components() { component.fmt_write(out)?; }
    write_crlf!(out, "END:{}", self.component_kind())?;
    Ok(())
}
```

Emission order for a `VTODO` is therefore fixed and **not** the input order:

1. `BEGIN:VTODO`
2. synthesized `DTSTAMP` if absent (`Utc::now()`)
3. all single properties, **alphabetically by key** (BTreeMap iteration)
4. synthesized `UID: <uuid v4>` if absent
5. all multi properties, alphabetically by key, then insertion order within a key
6. child components in insertion order
7. `END:VTODO`

`Calendar::fmt_write` (`src/calendar.rs:239-250`) writes `BEGIN:VCALENDAR`, then `self.properties` in
**Vec order** (calendar-level properties keep their order), then components, then `END:VCALENDAR`. It
does not synthesize `VERSION`/`PRODID` at write time — those come from `Calendar::default()`
(`src/calendar.rs:74-85`: `VERSION:2.0`, `PRODID:ICALENDAR-RS`, `CALSCALE:GREGORIAN`).
`Calendar::empty()` (`:112`) skips them.

Entry points: `Component::to_string()` (panicking, `:129`), `Component::try_into_string()` (`:134`),
`impl TryInto<String> for Todo` (via macro, `src/components.rs:651-657`), `Display for Calendar`
(`src/calendar.rs:299-303`), `TryInto<String> for &Calendar` (`:305`).

### Line writing, escaping, folding, CRLF

```rust
// src/properties.rs:193-214
pub(crate) fn to_line(&self) -> Result<String, fmt::Error> {
    let mut line = String::with_capacity(150);
    write!(line, "{}", self.key)?;
    for Parameter { key, val } in self.params.values() {
        write!(line, ";{}={}", key, Self::quote_if_contains_colon(val))?;
    }
    let value_type = self.value_type();
    match value_type {
        Some(ValueType::Text) => write!(line, ":{}", Self::escape_text(&self.val))?,
        _ => write!(line, ":{}", self.val)?,
    }
    Ok(line)
}
pub(crate) fn fmt_write<W: Write>(&self, out: &mut W) -> Result<(), fmt::Error> {
    let line = self.to_line()?;
    write_crlf!(out, "{}", fold_line(&line))?;
    Ok(())
}
```

- **Escaping** (`src/properties.rs:166-172`): only for `ValueType::Text` values, and only
  `\` → `\\`, `,` → `\,`, `;` → `\;`, `\n` → `\n`. **`\r` is not escaped or stripped**, and `:` is
  not escaped on write (though it *is* unescaped on read) — the escape/unescape pair is asymmetric.
- **Parameter values** are quoted only if they contain `:` or `;` (`:174-190`); already-quoted values
  pass through untouched.
- **Folding** at 75 bytes with `\r\n ` continuation, char-boundary aware (`src/properties.rs:384-420`).
- **CRLF**: every line, via the `write_crlf!` macro (`src/lib.rs:24-33`). Output is always CRLF.
- Property parameters iterate from a `BTreeMap<String, Parameter>` (`src/properties.rs:45`) — so
  parameter order is alphabetized too, and a repeated parameter key overwrites.

## LIMITATIONS

Each item was checked against the source; the ones marked **[V]** were additionally confirmed by
running code (output below).

### Round-trip / fidelity

1. **[V] Property order is not preserved.** Single properties are re-emitted alphabetically
   (`BTreeMap` at `src/components.rs:27`). A parsed VTODO does not serialize back byte-identically.
2. **[V] Repeated single-valued properties collapse to the last one.**
   `append_property` does `properties.insert(key, property)` (`src/components.rs:607-613`), and the
   parser builds the map with `.collect()` (`src/parser/components.rs:138-143`). Two `RELATED-TO`
   lines in → one line out, the second wins. Same for repeated `X-*`, `REQUEST-STATUS`, and any other
   property missing from `MULTIS`.
3. **[V] `RELATED-TO` is not a multi-property.** `MULTIS` lists the ABNF placeholder `"RELATED"`, not
   `"RELATED-TO"` (`src/parser/properties.rs:40`). Parent/child task hierarchies with more than one
   `RELATED-TO` are lossy. There is also no typed `RELATED-TO` accessor — raw property access only.
4. **[V] Serializing a component without `UID` mints a fresh random UUID every call**
   (`src/components.rs:108-110`), and without `DTSTAMP` stamps `Utc::now()` (`:99-102`). Two
   `to_string()` calls on the same value produce different bytes. This bites hardest on child
   `VALARM`s parsed from a file, which usually have neither.
5. **[V] Consequence of 4: parse → serialize → parse → serialize is not stable** for any VTODO that
   contains a `VALARM` (or that itself lacks UID/DTSTAMP).
6. **`\r` inside a text value is never escaped** (`escape_text`, `src/properties.rs:166-172`), so a
   CR in a `DESCRIPTION` emits a raw CR and corrupts the line structure.
7. Escape/unescape are asymmetric: reading unescapes `\:` and `\N`; writing produces neither.
8. Non-`Text` value types are never escaped on write, so an `X-*` property (which resolves to
   `ValueType::None`) containing `;` or `,` is emitted raw and will re-parse wrong.

### Missing VTODO properties (no typed API at all)

RFC 5545 §3.6.2 allows these in a VTODO; none has a setter or getter anywhere in the crate
(verified by grepping `src/` for each name outside `value_types.rs` and `parser/`):

- **`DURATION`** — no setter. `From<chrono::Duration> for Property` (`src/properties.rs:376-380`)
  exists, so `append_property(Duration::hours(2))` works, but **[V]** it emits `PT7200S`, not `PT2H`.
- **`GEO`**, **`RESOURCES`**, **`CATEGORIES`**, **`COMMENT`**, **`CONTACT`**, **`ATTACH`**,
  **`ORGANIZER`**, **`REQUEST-STATUS`**, **`RELATED-TO`** — raw `add_property` /
  `add_multi_property` only. (`CATEGORIES`, `COMMENT`, `CONTACT`, `ATTACH`, `RESOURCES` at least land
  in `multi_properties` correctly.)
- `TRANSP` is a VEVENT property and likewise has no accessor.
- There is **no `remove_uid`** on `Component` (`uid` and `get_uid` only, `src/components.rs:287-294`).

### VALARM inside VTODO

9. **`EventLike::alarm()` works for `Todo`** (`src/components.rs:569-572`) — writing a VALARM child
   into a VTODO is supported, and **[V]** a `VALARM` parsed from inside a `VTODO` is retained and
   re-emitted.
10. **[V] But a parsed alarm cannot be recovered as an `Alarm`.** `Component::components()` returns
    `&[Other]`, and there is no `From<Other> for Alarm`. Compiler output:
    `the trait `From<icalendar::components::other::Other>` is not implemented for `icalendar::Alarm``.
    Only `From<InnerComponent> for Alarm` exists, and `InnerComponent` is `pub(crate)`. You must read
    the alarm's fields as raw properties.
11. **[V] `Other` is not publicly nameable.** `src/lib.rs:48-64` re-exports `Component, Event,
    EventLike, Todo, Venue, Alarm, Related, Trigger, …` but **not** `Other`, while
    `Component::components() -> &[Other]` and `CalendarComponent::Other(Other)` both expose it.
    `icalendar::Other` fails to compile (`cannot find type `Other` in crate `icalendar``). You can
    call `Component` trait methods on the returned values but cannot write the type down, store it in
    a struct field, or write a function signature over it.
12. `Alarm`'s own getters (`get_action`, `get_trigger`, `get_description`, `get_repeat`) are
    `pub(self)` (`src/components/alarm.rs:195-217`) — unreachable from outside the crate even for an
    `Alarm` you built yourself.

### Type-model gaps

13. **[V] `Todo` inherits `EventLike`, so `ends()` / `get_end()` (`DTEND`) and `all_day()` are
    available on a VTODO** and will happily write a `DTEND` line, which RFC 5545 forbids in a VTODO
    (it uses `DUE` or `DURATION`). Nothing warns.
14. **[V] Unknown `STATUS` values are dropped from the typed view.** `get_status()` on
    `STATUS:BOGUS` returns `None` while the raw property is preserved. `TodoStatus` has no `Custom`
    variant (`src/properties.rs:300`) and `TodoStatus::from_str` is `pub(crate)`, so you cannot even
    parse a status string yourself through the crate.
15. **[V] `PRIORITY` semantics are wrong-ish for RFC.** `Component::priority()` clamps to `0..=10`
    (`src/components.rs:206-209`, `priority(99)` → `PRIORITY:10`) but RFC 5545 §3.8.1.9 defines
    `0` = undefined and `1..9` as the real range; `10` is out of spec. `get_priority()` returns
    `None` for a stored value `> 10` (`:226-229`) while leaving the raw property intact.
16. **`VJOURNAL`, `VFREEBUSY`, `VTIMEZONE` have no typed variant** — they fall into
    `CalendarComponent::Other` (`src/parser/components.rs:167`). **[V]** a `VJOURNAL` is counted by
    neither `todos()` nor `events()`. `src/lib.rs:71` still carries the TODO:
    `// TODO Calendar TimeZone VTIMEZONE STANDARD DAYLIGHT (see thunderbird exports)`.
17. **Recurrence is compiled out here.** `EventLike::recurrence()` / `get_recurrence()` are
    `#[cfg(feature = "recurrence")]` (`src/components.rs:460,506`) and neither `caldir-core` nor
    `caldir-provider-webcal` enables that feature. `RRULE` on a VTODO is raw-property-only today.
    (`caldir-core` depends on `rrule = "0.14"` directly instead.)
18. `chrono-tz` is likewise not enabled, so `CalendarDateTime::from_ymd_hm_tzid`,
    `as_dt_with_tz`, and `ymd_hm_tzid` are unavailable. **[V]** The
    `CalendarDateTime::WithTimezone { date_time, tzid }` variant itself is *not* feature-gated
    (`src/components/date_time.rs:61-67`), so `DUE;TZID=Europe/Berlin:…` parses and re-serializes
    correctly — you just get the TZID as a `String` with no `chrono_tz::Tz` conversion.
19. **[V] `COMPLETED` must be UTC to be readable.** `get_completed()` returns `None` for
    `COMPLETED:20260105T093000` (floating), even though the property is retained. RFC 5545 does
    require UTC here, so this is a strictness choice, not a bug — but it means "value present but
    unreadable" is a real state.
20. `Calendar::from_str`'s error type is `String` (`src/parser/calendar.rs:133`) — no error kind, no
    line/column struct, so caldir cannot classify parse failures programmatically.
21. **[V] Duplicate UIDs are not deduplicated or detected.** Two `VTODO`s with `UID:a` both survive.
22. `DatePerhapsTime::from_property` falls back to bare `DATE` parsing when `VALUE=DATE` is absent
    unless the `strict-dates` feature is on (`src/components/date_time.rs:298-328`) — lenient here.
