# W3-C3: A failed CalDAV delete lookup must not report success

**Needs:** P3-04 (`737164c`), P2-04 (`151c720`), W2-C3 (`c07850e`)
**Origin:** Wave 3 data-loss review, LOW — but it makes the two providers disagree

## The defect
`caldir-provider-caldav/src/caldav/ops/delete_event.rs`:

```rust
let href = match location {
    Ok(loc) => loc.href,
    Err(_) => {
        // Event not found on server — treat as already deleted
        return Ok(());
    }
};
```

`find_event_location` can fail for reasons that are **not** "the resource is absent": a network
error, a 5xx on the fallback UID-filtered REPORT, an auth failure, a malformed multistatus. All of
them are reported to core as a **successful delete**.

Concrete path: a task delete is dispatched; `{uid}.ics` does not hold the task (normal — the server
assigned its own filename); the fallback REPORT 500s transiently; `delete_event` returns `Ok(())`;
core records the delete as synced. Nothing was deleted, nothing was confirmed absent, and the user
is never told.

Bounded by the sync model — the local file is already gone and C-12 keeps bases insert-only, so a
later pull most likely re-resolves to "retry the delete" rather than resurrecting anything. So this
is a **retry-swallowing and observability** defect rather than outright loss. It still violates the
standing rule: *preserve data > skip the destructive action > **surface an explicit error***.

## Why it is worth fixing now, despite being pre-existing
1. **The providers now disagree on the same semantic.** `P5-03` (`5f5d659`) got this right for
   Google: `classify_delete_status` returns `Ok(())` for success **or 404**, and an error for
   everything else — pinned by `a_genuine_api_failure_is_not_read_as_already_deleted`. CalDAV
   should not be the one that lies.
2. **The mechanism did not exist when the code was written.** `P3-04` was explicitly told to leave
   this alone because the error taxonomy was `P2-04`'s job. `P2-04` and `W2-C3` have since landed:
   `caldir_core::provider::classified_error(ErrorCode::RemoteNotFound, ..)` is available and proven
   reachable from a provider crate.
3. **Wave 3 newly routes real task deletes through this branch.** It was event-only when written.

## Acceptance criteria
1. A genuinely absent resource is still a **successful** delete — deleting what is already gone
   achieved the goal. Do not regress that.
2. A lookup failure that is **not** an absence (network, 5xx, auth, malformed response) propagates
   as an error rather than a success.
3. A test distinguishes the two, in the shape `P5-03`'s
   `a_genuine_api_failure_is_not_read_as_already_deleted` uses. Assert on **outcome**, not on a
   status code you do not control.
4. Prefer surfacing the absence case as `ErrorCode::RemoteNotFound` where it fits the existing
   error flow — but **only if that does not turn criterion 1 into a failure**. A successful no-op
   must stay a success.
5. `deleting_a_task_leaves_a_same_uid_event_alone` and
   `a_task_already_absent_from_the_server_is_a_successful_delete` stay green, unmodified.

## Non-goals
- No change to `find_event_location`'s own resolution logic — component-aware identity is settled
  and reviewed SAFE.
- No change to the Google provider; `P5-03` is already correct.
- No widening of the existing `404` string sniff beyond what criterion 2 needs.
