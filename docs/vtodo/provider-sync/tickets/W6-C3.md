# W6-C3: Strip the remaining `D-<n>` decision references from shipped code

**Needs:** W6-C1 (`9e83140`) · **Origin:** W6-C1's own discovered issue · **Last code-touching ticket**

## Why this exists separately
`W6-C1` swept ~100 internal identifiers (`P*-**`, `W*-C*`, `C-*`, `S*`, `CROSS-*`, `CALDAV-*`,
`GOOGLE-*`) out of shipped non-test code and left **`D-<n>` untouched** — correctly, because
`D-<n>` is absent from that ticket's literally-specified acceptance grep. It scoped conservatively
rather than expanding, and flagged the remainder. That was the right call; this ticket finishes it.

**Measured now: 18 occurrences in production comments** — 12 × `D-2`, 3 × `D-3`, 3 × `D-4`.

These are approved-decision ids from `docs/vtodo/provider-sync/tickets/INDEX.md` §1. They resolve
only into internal planning material, which is exactly the property that made every other identifier
worth removing: an out-of-tree reader — the Proton provider author `D-5` was written for — hits
`D-2` in a doc comment with no way to look it up.

## The rule — unchanged from W6-C1
**Keep the reasoning. Drop only the label.**

- Before: `// Fails closed (D-2/C-8): an absent capability reads as false.`
- After: `// Fails closed: an absent capability reads as false.`

**Do not delete a comment because it carries an identifier.** The rationale is the valuable part.
Where dropping the label leaves a dangling sentence, repair the sentence. If a comment is *only* a
bare citation, replace it with the one-line reason it stood for.

The decisions themselves are worth stating in plain words where they aren't already — `D-2` means
*capabilities are per-remote and fetched at execution time*; `D-3` means *the write boundary carries
`CalendarItem`*; `D-4` means *Google is explicitly lossy, with no invented equivalents*. Prefer the
substance over the label.

## Scope
- **In scope:** non-test regions of tracked `.rs` files, every crate.
- **Out of scope:** `#[cfg(test)]` blocks (including a doc comment attached to one), test names,
  integration-test crates under `tests/`, and everything under `docs/`.
- **Leave alone:** RFC references, shipped-core requirement numbers (`R92`, `R68`, `R55`), spec
  section marks (`§16`), HTTP status codes, standard property names.

## Two hard constraints, carried from W6-C1
1. **Zero executable line changes.** `git diff` must touch comments only — no attribute removals
   this time; `W6-C1` already handled the one that was warranted.
2. **The test count must be identical before and after.** Record it both ways, by scope.

## Do not disturb P6-04's scans
`caldir-core/tests/provider_neutrality.rs` holds two source-scanning tests that assert on **code
shapes, not comment prose**. Run that file before and after; both must pass. If the result changes,
you edited code.

## Acceptance criteria
1. A grep for `\bD-[0-9]\b` over non-test regions of tracked `.rs` files returns nothing. Include
   the grep in the report.
2. Every touched comment still explains *why*. Show at least four before/after samples.
3. `cargo fmt --check`, `cargo clippy --workspace --all-targets`, `cargo test --workspace` green,
   with the test count unchanged.
