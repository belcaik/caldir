# W3-C1: CalDAV capabilities must be per-remote and honest

**Needs:** P3-01 (landed, `b979358`) · **Origin:** orchestrator verification, HIGH (data-loss)
**Blocks:** P3-02, P3-03, P3-04

## The defect
`caldir-provider-caldav/src/commands/capabilities.rs::handle` ignores `_cmd` and returns
`tasks: { read: true, write: true }` unconditionally. Meanwhile `caldav/ops/list_events.rs`
may **degrade** a rejected VTODO REPORT into an events-only `Ok` when
`collection_openly_lacks_vtodo` is true.

Those two behaviours combine into a task-deleting path:

1. A collection has synced VTODOs before, so sync bases exist for them.
2. Its `supported-calendar-component-set` omits `VTODO` — wrongly, or because the server
   changed. **C-14 establishes by measurement that this advertisement can be wrong**: a VEVENT
   PUT into a VTODO-only collection returned `201`.
3. The VTODO REPORT fails for any reason. `collection_openly_lacks_vtodo` returns `true`.
4. `fetch_events` degrades and returns `Ok` holding **events only**.
5. `capabilities` still answers `tasks.read = true`, so `P2-06` lifts the
   `suppressed_task_deletes` belt.
6. Core reads the degraded listing as complete remote state. Every local VTODO holding a base is
   absent from it, so each becomes an **incoming delete**.

This is C-7a's hazard, and P3-01 is the ticket that armed it — before P3-01 no provider
overrode the events-only default, which is the only reason it was inert.

## The tension is real, and both sides must hold
- **R2/C13** (P3-01's own fix): a rejected VTODO REPORT MUST NOT break a working event-only sync.
  Making the degrade fatal reintroduces that regression.
- **C-7a**: a degraded task enumeration MUST NOT be presented to core as complete task state.

Making the degrade an error satisfies C-7a and breaks R2/C13. Leaving it as-is satisfies R2/C13
and deletes tasks. **Neither is acceptable.**

D-2 already resolves it: **capabilities are per-remote, not per-binary.** Degrade the *listing*
while reporting `tasks.read = false` **for that remote**. Events keep syncing; the belt stays on;
no task is deleted. Both constraints hold at once.

## Acceptance criteria
1. `handle` consults `cmd.remote`. A remote whose collection cannot honestly serve a task query
   reports `tasks.read = false`.
2. **Fail closed (C-8).** Absent, unknown, or unreadable task-capability information reports
   `tasks.read = false`, never `true`. `P3-01` already records `caldav_supports_tasks` in
   `RemoteConfigParams` and omits it — rather than writing `false` — when unknown; absent MUST
   read as `false` here.
3. A test drives the full hazard: bases present, component set omitting `VTODO`, REPORT
   rejected, listing degraded — and asserts **no local VTODO is deleted**. Assert on the diff's
   incoming set and on the files on disk, not on the counter alone.
4. Event-only sync against a server with no VTODO support still works. `P3-01`'s
   `a_rejected_vtodo_report_does_not_break_an_event_only_listing` stays green, unmodified.
5. **C-14 still holds:** the component-set property fires zero extra requests on the happy path
   and never gates the VTODO REPORT. `a_healthy_listing_never_asks_for_the_component_set` stays
   green, unmodified.

## Sequencing note — `tasks.write`
`P3-01` also declares `tasks.write = true`, but `P3-02`/`P3-03`/`P3-04` have not landed, so a
task write reaching the CalDAV provider hits `P1-04`'s unsupported-arm gate and errors. That is
loud, not silent, so it is **not** a data-loss defect — but until those tickets land, a mixed
calendar now *fails* on a task push where it previously withheld it cleanly.

Decide deliberately and state the choice: either hold `tasks.write = false` until `P3-04` lands,
or accept the noisy interval. **Do not leave it undecided.**

## Non-goals
- No VTODO create/update/delete — `P3-02`/`P3-03`/`P3-04`.
- No change to core. This is a provider-side honesty fix.

## Residual gap — carried to P3-07
Closed compositionally, not end to end. `caldir-core` must never depend on a provider crate, and
its seams (`Provider`, `ProviderTransport`, `CalendarDiff::compute_from_listing`, `MockProvider`)
are `pub(crate)`, so no single test binary can run the real CalDAV provider inside core's diff
engine. The proof is two halves:

- core's `a_task_reading_provider_reporting_no_tasks_deletes_the_local_task` shows
  `tasks.read=true` + an events-only listing deletes every local task holding a base;
- this ticket's tests show the provider now reports `tasks.read=false` for such a collection.

Sound, but nothing executes the join. **`P3-07` (Radicale E2E) is the only place that can**, and it
MUST cover it: a collection whose component set omits `VTODO`, a rejected VTODO REPORT, local tasks
holding sync bases — and no local task deleted, asserted against files on disk.
