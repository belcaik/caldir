# W6-C2: Name the provider and method on an uncoded provider error

**Needs:** P6-02 (`8141f65`) · **Origin:** P6-02 escalation, LOW (diagnostics, not data safety)

## The finding
`P6-02` built a real pre-`P1-01` stub binary and drove it as a subprocess. Such a binary — one that
predates the `RawRequest` envelope decode *and* the `code` field — answers an unknown `capabilities`
verb with its own parse failure:

```
{"status":"error","error":"Failed to parse request: unknown variant `capabilities`, expected one of `connect`, ..."}
```

No `code` field, because it predates that too. `classify(error, None)` therefore returns
`ProviderError::Provider(error)` — the generic arm, message passed through **verbatim**.

**Effect is correct and safe:** `Provider::call` returns `Err`, `Remote::capabilities()` folds it to
the all-false fail-closed value, and the sync proceeds task-less with local VTODOs preserved.
`P6-02` proved that end to end.

**Diagnostics are not.** Spec §17 requires an old binary to fail with *"a clear version/capability
error, not malformed JSON or undefined behavior."* What this vintage actually produces reads as a
parse error and never names the provider. A post-`P1-01` binary does better — it returns a typed
`unsupported_method` code and a message naming both — so the guarantee holds for the newer vintage
and degrades for the older one, which is the one an out-of-tree Proton install will actually be
running at upgrade time.

## Why the fix is small
`Provider` already carries `slug: ProviderSlug` (`caldir-core/src/provider.rs`), and
`Remote::capabilities()` knows the method it called. The context §17 asks for is available at the
call site and simply unused on the generic arm.

## Acceptance criteria
1. A generic, uncoded provider error surfaces with the **provider name** and the **RPC method**
   attached, so it reads as a version/capability problem rather than a parse failure.
2. **The original provider text survives.** Wrap, do not replace — a provider's own diagnostic is
   often the only clue to what actually went wrong.
3. A **typed** error (any `ErrorCode`) keeps its existing class and message. This changes the
   generic arm only; `P2-04`'s taxonomy and `W2-C2`'s mapping tests stay green, unmodified.
4. `P6-02`'s three subprocess tests stay green. Update an assertion only if the new wrapping makes
   it literally false, and show the before/after if so.
5. Fail-closed behaviour is **unchanged** — this is a message change, not a control-flow change.
   `Remote::capabilities()` still never propagates; every failure still yields the all-false value.

## Non-goals
- No new `ErrorCode` variant — the six §16 classes are settled.
- No change to `classify`'s mapping (`W2-C2` pins it).
- No wire change of any kind. No serialized string, no JSON key, no public signature.
