## Responsibility
One property, proved end to end: the Google task id is **minted once, stored once, and reused**.
`create → sync → sync` yields exactly one remote task; the same id resolves the update and the
delete; and `X-GOOGLE-TASK-ID` never becomes the `UID` and never appears twice on the same item.
This ticket writes no production logic — it is the lock over `P5-01..03`'s three seams, plus the
credential-gated live tier that is the only place the sequence is genuinely observable.

## RED tests
Tests 1–3 are **necessary conditions**, not the proof. Test 4 is the proof. Say so in the test
module's doc comment; a reviewer who reads tests 1–3 as establishing "no duplicates" has been
misled, and that is the exact failure this ticket exists to prevent.

- **ADD** `google_task::tests::the_google_task_id_is_provider_metadata_and_never_the_uid`
  (`caldir-provider-google/src/google_task/mod.rs`). A `Todo` canonicalized from a create response
  has `uid` equal to the local task's and `X-GOOGLE-TASK-ID` equal to Google's `id`, and the two
  strings differ. Right proof: §6's separation is invisible when a test uses the same value for
  both, which is the shape a "just use the id as the UID" implementation produces and passes.
- **ADD** `google_task::tests::the_minted_id_appears_exactly_once_after_a_second_cycle`
  (same file). Run the canonicalization twice — canonical₁ → `to_google` → a stubbed Tasks response
  echoing the same `id` → canonical₂ — and assert `x_properties` contains exactly **one**
  `X-GOOGLE-TASK-ID`, with the same value both times. Right proof: C-13's merge unions two
  `x_properties` vectors, and the naive union duplicates the key. A duplicated `X-GOOGLE-TASK-ID`
  serializes two properties into the local `.ics`, after which `Todo`'s `x_properties_eq` comparison
  reports a difference against the base forever — churn dressed up as an identity bug.
- **ADD** `google_task::tests::the_minted_id_resolves_both_the_update_and_the_delete` (same file).
  Feed canonical₁ into `P5-02`'s patch-URL builder and `P5-03`'s delete-URL builder; assert both
  address the same task id. Right proof: it is the only assertion that binds the three seams to one
  identity rather than three independently-correct string handlers.
- **ADD** `live::google_tasks::create_sync_sync_yields_exactly_one_remote_task`
  (new `caldir-provider-google/src/live/google_tasks.rs`, gated on `CALDIR_LIVE_GOOGLE=1` by a
  runtime `live_enabled()` mirroring `caldir-provider-caldav/src/live/radicale.rs`). Create a task,
  sync, sync again; list the remote task list and assert **exactly one** task with that title
  exists, and that its id equals the id stored locally. Then update, sync, sync; then delete, sync;
  assert absent. Right proof: §6's *"A second sync after a successful create MUST NOT create a
  duplicate"* is a statement about two consecutive runs against a real service. No pure function
  observes it — the duplicate is created by the *second* call deciding the task is new, which only
  a real second call can demonstrate.

## Acceptance criteria
1. `uid` and `X-GOOGLE-TASK-ID` are distinct values and neither derives from the other. (§6, §12)
2. `X-GOOGLE-TASK-ID` is present exactly once on a canonical item after any number of cycles. (C-13)
3. The same id resolves create's response, update's target and delete's target. (`GOOGLE-9`)
4. Under the live gate, `create → sync → sync` leaves exactly one remote task. (§6)
5. Under the live gate, `update → sync → sync` leaves exactly one remote task with the new content,
   and `delete → sync` leaves none. (§15)
6. The live tier is a **runtime** gate on `CALDIR_LIVE_GOOGLE=1`, not `#[ignore]`, and its exact
   command and expected output are recorded for `P6-05`. (§24, radicale.rs's `live_enabled`)
7. The test module states plainly which tests are necessary conditions and which is the proof.
8. `just check` green; the unit tests pass with the gate unset.

## Non-goals
- **Any production logic.** If a test here fails, the fix lands in `P5-01`, `P5-02` or `P5-03` — or,
  for a stripped `X-GOOGLE-TASK-ID` on update, in `P2-01`/C-13. Do not repair a seam from inside its
  lock.
- **The DUE fixpoint and the no-changes assertion** — `P5-05` owns canonicalization churn and
  `P5-07` owns the closing verification. This ticket's live test asserts *cardinality and identity*;
  theirs assert *no changes*.
- **Base removal** — there is none (C-12).
- **`tasks.write=true`** — `P5-07`.
- **CalDAV's equivalent** — `P3-07`.

## Notes for the implementer
- **A provider crate cannot reach core's mocks.** Grep-verified: `caldir-core/src/test_utils.rs` is
  `#[cfg(test)]` and unexported, and `MockProvider`
  (`caldir-core/src/provider/mock_provider.rs`) is `pub(crate)`
  (`docs/vtodo/context/testing.md` §4, §8). There is therefore no way to drive
  `Connection::diff` / `apply_outgoing_diff` from here. That is why test 4 is a live test rather
  than a `MockProvider` sequence; if the maintainer wants a non-credentialed end-to-end, its home is
  `P6-04`'s workspace regression, with a `MockProvider` scripted to answer like Google Tasks.
- **`MockProvider` holds one queued response at a time** (`set_response`), so even in core a
  two-cycle sequence must re-stub between calls. Do not write a test that assumes a queue.
- **The duplicate is created by the second run, not the first.** Every implementation looks correct
  after one sync. Never accept a single-cycle assertion as evidence for criterion 4.
- The live test must clean up after itself — delete the task it created even on failure — or the
  next run starts with a duplicate already present and the assertion becomes meaningless.
- `Todo`'s `PartialEq` is `educe`-derived and **ignores** `created`, `last_modified` and `sequence`
  (`caldir-core/src/todo.rs`), and compares `x_properties` through `x_properties_eq`. That is the
  comparison the diff uses, so it is the comparison these tests should use — not a string compare of
  serialized ICS, which would fail on `DTSTAMP` alone.
- `Todo` has no `x_property()` accessor (only `Event` does). Use the helper `P5-01` added in
  `google_task/mod.rs`, and have it assert single-occurrence rather than returning the first match.
