# W2-C1: Make the §16 error taxonomy reachable by its consumer

**Needs:** P2-04 (landed, `151c720`) · **Origin:** Wave 2 review finding, HIGH

## Responsibility
`P2-04` built the six §16 classes so "the CLI can distinguish them without string matching"
(its Responsibility, acceptance criterion 4, and its `CROSS-4` proof claim). It cannot.
`ProviderError` is re-exported `pub(crate)` (`caldir-core/src/provider.rs`), so no downstream
crate — `caldir-cli` or the out-of-tree Proton provider — can name or match it. The reviewer
confirmed with a compile probe: **E0603, "enum `ProviderError` is private."**

Today every downstream caller reaches only the human-readable `Display` string — which is exactly
the string matching `P2-04` exists to eliminate.

## This was a deferred decision, not an oversight
`P1-01`'s implementer notes say verbatim: *"Do not assume a new variant is publicly nameable; if
`P2-04` needs it to be, that is `P2-04`'s call, not a drive-by here."* `P2-04` built on the
constraint without resolving it. This ticket resolves it.

## Acceptance criterion — one outcome, mechanism is the implementer's call
**A downstream crate distinguishes all six §16 classes without inspecting message text**, proven
by a test in `caldir-core/tests/public_error_api.rs` — a separately compiled crate that sees only
what a downstream consumer sees. An in-crate `#[cfg(test)]` test does **not** satisfy this: it has
private-item access and proves nothing about the public surface.

Two bounded options. Either is acceptable; state which you chose and why.

- **A — expose `ProviderError`.** Make the re-export `pub`. It is already `#[non_exhaustive]`, so
  downstream matches must carry a wildcard arm and adding a seventh class later stays
  source-compatible.
- **B — expose the class through `RemoteError`.** Keep `ProviderError` crate-internal and surface
  the class as a typed accessor on the public, `#[non_exhaustive]` `RemoteError`
  (e.g. returning `Option<rpc::ErrorCode>`, which is already `pub`). Narrower public surface;
  costs an accessor.

**Preference: B**, if it is clean — it keeps the internal error type internal and widens the API
by exactly what the consumer needs. Take A if B forces awkward plumbing.

## Also in scope — the adjacent doc overstatement (review LOW)
`provider-author-guide.md`'s "six failure classes" section tells authors they "can opt into a
specific class where one applies." No provider can. The only mechanism attaching a class to a
`Handler` error is `Classified`, a private struct in `handler.rs` usable only by core's own trait
defaults. In-tree and out-of-tree providers alike can produce **none** of `MissingAuthScope`,
`RemoteNotFound`, `Conflict`, `SemanticLimitation`, or `Network` today.

Either give providers a public way to attach a class, or correct the copy to describe what
actually exists and name the ticket that will deliver the rest. **Do not leave the guide promising
a capability that does not ship** — its readers cannot check it against source, which is the whole
premise of D-5.

## Non-goals
- No new error class. The six are settled.
- No provider-side production of classes — Waves 3/5 (`P3-02`, `P3-03`, `P4-02`).
- No CLI copy change; `P2-05` is done. This makes the class *reachable*, not rendered.

## Note for P3-02/P3-03/P4-02
If providers still cannot attach a class after this ticket, those tickets are blocked from
producing anything but `UnsupportedOperation`. Resolve it here or say plainly that it is deferred.
