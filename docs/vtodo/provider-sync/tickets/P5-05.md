# P5-05: Google due-date canonicalization

> **Carried forward from `P4-04` (`4a34179`) — the C-18 hazard is YOURS, not P4-04's.**
> `P4-04` mapped Google `due` -> `DUE` and is C-18-safe, but only because Google always sends an
> explicit-offset RFC 3339 timestamp, so `google_due_to_date` reads the offset off the value itself
> and D-4's "system zone otherwise" branch is unreachable there. It takes no zone parameter and
> asserts no production `DUE` value.
>
> **The write direction is where C-18 actually bites.** A local `VTODO`'s `DUE` is an ICS value in
> the user's own zone, and `EventTime::to_utc` is
> `to_local_tz(&chrono::Local).with_timezone(&Utc)` — reaching for it moves the whole u_crawler
> deadline set **one calendar day late**. Nothing in Waves 1-4 exercises that.
>
> So this ticket MUST: take the zone as a parameter (never `chrono::Local` implicitly); derive the
> date from the `DUE`'s own zone when it has one and the system zone otherwise, with the offset from
> the zone database and never a constant; and **assert the real production fixture values by name**
> from `caldir-core/src/test_utils.rs` -- `VTODO_OPEN_PRODUCTION_ICS` (`DUE:20260902T035959Z`) and
> `VTODO_COMPLETED_PRODUCTION_ICS` (`DUE:20260708T035959Z`), both 23:59:59 on the *previous* local
> day in `America/Santiago`.
>
> Per C-18's amendment, the measured distribution is 44 x `T035959Z`, 12 x `T025959Z`, and one
> outlier at `T025900Z`. **Assert no `5959Z` suffix rule** -- it is false for one production file.


**Provides:** —  **Needs:** `P5-01`, `P4-04`

## Responsibility
The one function that decides what a `DUE` becomes on the way to Google, and what a Google `due`
becomes on the way back, plus the fixpoint that keeps the pair from oscillating. A datetime `DUE`
converts to its **local calendar date** under the system zone; the canonical remote value is
**date-only**; and because `push_outgoing_changes` writes the item the provider returns over both
the local file and the sync base, the truncation happens exactly once and never again. Permanent
sync churn is the failure this ticket exists to make unreachable.

## Requirements satisfied
- **§13** — *"Google Tasks due dates have date precision; the API does not preserve due time."*,
  *"A VTODO such as: DUE:20260901T235900Z cannot round-trip exactly through Google Tasks. This MUST
  be treated as a provider semantic limitation, not a parser bug."*, and the preferred policy
  verbatim: *"1. local -> Google: convert DUE to its calendar date according to a documented
  timezone rule; 2. Google -> local: represent the remote value as a date-only DUE; 3. after a
  successful push: store the canonical remote representation in the sync base so repeated syncs do
  not report the same loss forever."* And its two prohibitions: *"The provider MUST NOT silently
  pretend the timestamp survived."* / *"Tests MUST prove that timestamp truncation does not create
  permanent sync churn."*
- **§7** — *"Provider canonicalization MUST NOT create permanent sync churn."*
- **§15** — *"Provider canonicalization MUST feed back into the sync base."* and the
  *"first sync: create / second sync: no changes"* sequence.
- **D-4**, binding in detail — *"a datetime `DUE` pushed to Google converts to the corresponding
  local calendar date under the timezone policy already available in context; the canonical remote
  value is date-only; after push the sync base holds the canonical representation so the truncation
  never becomes permanent churn."*
- Proves **`GOOGLE-8`** (*"DUE obeys documented Google date-only canonicalization."*) and
  **`GOOGLE-10`** (*"A second sync reports no changes after canonicalization."*).

## RED tests
Put the conversion in `caldir-provider-google/src/google_task/due.rs` as a pair of pure functions
taking the target zone **as a parameter** — `fn google_due_date<Tz: TimeZone>(due: &EventTime, tz:
&Tz) -> NaiveDate` and its inverse — with the command path passing `chrono::Local`. That mirrors
`EventTime::to_local_tz`'s own signature and lets these tests name a zone without mutating process
environment (this crate has no `serial_test` dev-dependency, and `chrono-tz 0.10` is already a
dependency).

- **ADD** `google_task::due::tests::a_late_evening_local_deadline_keeps_its_local_calendar_date`.
  `DUE:20260902T035959Z` under `chrono_tz::America::Santiago` yields **`2026-09-01`**. Right proof:
  this is a verbatim production value — every one of the 57 `P1-05` VTODOs carries a `DUE` of this
  shape, and 03:59:59Z is 23:59:59 the *previous* local day. The natural implementation
  (`due.to_utc().date_naive()`, or `EventTime::to_utc` followed by a date) yields `2026-09-02` and
  moves the entire u_crawler deadline set one day late. A UTC-only test passes for both
  implementations and proves nothing.
- **ADD** `google_task::due::tests::the_offset_comes_from_the_zone_database_not_a_constant`.
  `DUE:20260909T025959Z` under `America/Santiago` yields **`2026-09-08`**. Right proof: the archive
  holds both `T035959Z` and `T025959Z` deadlines because the zone changes offset between them. A
  hard-coded −4 gets the first right and the second wrong, and that is a bug that only appears in
  September.
- **ADD** `google_task::due::tests::a_zoned_due_uses_its_own_tzid_before_the_system_zone`. A
  `EventTime::DateTimeZoned { tzid: "Europe/Stockholm", .. }` at `00:30` resolves through its own
  TZID to an instant, then to a date in the passed zone. Right proof: `Todo::due` can hold any of
  four `EventTime` variants and each converts differently; `to_local_tz` already handles all four,
  a hand-rolled `match` typically forgets `DateTimeFloating`.
- **ADD** `google_task::from_google::tests::a_google_due_becomes_a_date_only_due_never_a_midnight_timestamp`.
  Google's `"2026-09-01T00:00:00.000Z"` parses to `EventTime::Date(2026-09-01)`, asserted with an
  exhaustive `match` so `DateTimeUtc` fails the test. Right proof: §13 clause 2 says *date-only*.
  Google returns a timestamp, so the honest-looking implementation (reuse
  `google_dt_to_event_time`) produces `DateTimeUtc(midnight)` — which then differs from the local
  file's date-only `DUE` on every comparison. That is the churn, and only an exhaustive match
  catches it.
- **ADD** `google_task::due::tests::an_undated_task_stays_undated`. `due: None` sends no `due`
  field; a Google task with no `due` parses to `due: None`. Right proof: `Todo::occurs_in_range`
  already refuses to synthesize a date because a fabricated one makes an undated task unpushable.
  Inventing "today" here would push a wrong deadline to the user's phone.
- **ADD** `google_task::due::tests::the_canonical_due_is_a_fixpoint`. canonical₁ → `to_google` →
  a stub echoing Google's canonicalization → `from_google` → canonical₂; `canonical₁.due ==
  canonical₂.due`, run under `UTC`, `Europe/Stockholm` and `America/New_York` plus
  `America/Santiago`. **Necessary, not sufficient** — state that in the test's comment.
- **ADD** `live::google_tasks::create_sync_sync_reports_no_changes_for_a_timestamped_due`
  (`caldir-provider-google/src/live/google_tasks.rs`, the module `P5-04` creates, gated at runtime
  on `CALDIR_LIVE_GOOGLE=1`). Push a `P1-05` fixture task carrying `DUE:20260902T035959Z`; sync;
  sync again; assert the second run reports **no changes**. Right proof: `GOOGLE-10` is a statement
  about two consecutive runs against a real service. The fixpoint test above proves the conversion
  agrees with itself; it does **not** prove that Google agrees with the conversion, and Google is
  the party that truncates.

## Acceptance criteria
1. A datetime `DUE` converts to its calendar date **in the system zone**, resolved through the zone
   database. (§13 clause 1, D-4, CLAUDE.md §Timezones)
2. A Google `due` becomes `EventTime::Date`, never a midnight `DateTimeUtc`. (§13 clause 2)
3. The canonical item returned from a push carries the date-only `DUE`, so
   `push_outgoing_changes` writes it to both the local file and the base. (§13 clause 3, §15, C-2)
4. Applying the conversion to an already-canonical item is a no-op. (§7)
5. `due: None` stays `None` in both directions; no date is ever synthesized. (`Todo::occurs_in_range`)
6. The loss is documented in `docs/vtodo/provider-sync/providers/google-tasks.md` as *lossy*, not as
   round-tripped. (§13's *"MUST NOT silently pretend the timestamp survived"*, `P5-06` owns the
   table)
7. The live gate demonstrates a second sync reporting no changes for a timestamped `DUE`.
   (`GOOGLE-10`, §24)
8. `just check` green; every unit test passes under all four zones.

## Notes for the implementer
- **The verified production trap, in one line:** every `P1-05` VTODO's `DUE` is a UTC instant at
  `T035959Z` or `T025959Z`, which is 23:59:59 **the previous day** in the fixture author's zone.
  `EventTime::to_utc()` is the wrong function — it is defined as
  `self.to_local_tz(&chrono::Local).with_timezone(&Utc)`, i.e. it *ends* in UTC. Take the date from
  `to_local_tz(tz)`, before any `with_timezone(&Utc)`.
- **Google's `due` is a timestamp field whose time-of-day the API discards**, and it is returned as
  midnight UTC. Reading that midnight back as a time is how the churn starts. Do not write
  `T00:00:00.000Z` into a local `DUE`.
- **Do not reuse `google_dt_to_event_time`** (`google_event/from_google.rs`). It is correct for
  events and wrong here by construction.
- **The churn is invisible in a single cycle.** Local file says `DUE:20260902T035959Z`, base says
  the same, push truncates, and everything looks fine — until the next `diff` compares the local
  file against a base that now says `DUE;VALUE=DATE:20260901`. It is `push_outgoing_changes`
  rewriting the local file from the returned item that closes this, and only if `P5-01` returns the
  **response**. If it returns the request item, no amount of correctness here helps.
- Take the zone as a parameter. `chrono::Local` reads the process `TZ`, and this crate has no
  `serial_test` dev-dependency, so a test that mutates `TZ` races every other test in the binary.
- **The `P1-05` fixtures live in `caldir-core/src/test_utils.rs`, which this crate cannot reach.**
  Grep-verified: `test_utils` is `#[cfg(test)] mod test_utils;` and unexported
  (`docs/vtodo/context/testing.md` §4). Copy the ICS literals into this crate's test module as
  inline `\r\n` string constants, matching the no-fixture-files convention, and keep them
  byte-identical to `P1-05`'s so a divergence is a visible diff rather than a silent drift.
- Pass the whole `P1-05` set through the conversion in one loop and assert the fixpoint on each; 57
  real values cost nothing to run and cover the DST boundary for free.
