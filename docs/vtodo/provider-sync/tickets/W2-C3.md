# W2-C3: A public way for a provider to attach a §16 error class

**Needs:** W2-C1 (landed, `7772362`) · **Origin:** P4-02 escalation + Wave 2 review LOW
**Blocks:** P3-03 (ETag/precondition → `Conflict`), and any provider reporting a §16 class

## The gap
`W2-C1` made `ProviderError` and `ProviderTransportError` `pub`, so a **consumer** can now
distinguish the six §16 classes. Nothing lets a **producer** attach one. The only mechanism is
`Classified`, a struct private to `caldir-core`'s `handler.rs`, used solely by the trait defaults
to tag their own `unsupported_operation` refusal.

So a provider binary — in-tree or the out-of-tree Proton one — can produce `unsupported_operation`
and nothing else. `missing_auth_scope`, `remote_not_found`, `conflict`, `semantic_limitation` and
`network` are unreachable from a `Handler` implementation.

`P4-02` hit this wall, reported it rather than inventing a mechanism, and recommended the shape
below. The provider-author guide already tells readers the gap exists and names the tickets that
would close it.

## Recommended shape (from P4-02's escalation)
A minimal public constructor exported from `caldir_core::provider`, e.g.

```rust
pub fn classified_error(code: rpc::ErrorCode, msg: impl Into<String>) -> Error
```

Chosen over the alternatives because it is the smallest surface change and **does not touch the
`Handler` trait signatures the wire protocol already stabilized around** — Proton compiles against
those. Rejected alternatives: making `Classified` itself public (leaks an implementation type), and
widening `Handler`'s `Result<T, Error>` alias to carry a code (breaks every provider's signatures).

Implement this shape unless you find a concrete reason it fails; if so, escalate rather than
substituting a different design silently.

## Acceptance criteria
1. A provider crate can attach any of the six §16 classes to an error it returns from a `Handler`
   method, using only `caldir-core`'s public API.
2. The class survives the wire round trip and arrives as the matching `ProviderError` variant —
   proven end to end, not by unit-testing the constructor.
3. **Wire compatibility is unchanged.** No serialized `command` string, no JSON payload key, and
   no existing public signature changes. An error envelope without `code` still decodes; an
   unknown `code` still degrades to the generic variant (C-16, R55).
4. A provider that attaches no class behaves exactly as today.
5. `caldir-core/tests/public_error_api.rs` proves the constructor is reachable and usable from a
   separately compiled crate — the same bar `W2-C1` met. An in-crate test does not satisfy this.
6. `docs/vtodo/provider-sync/provider-author-guide.md`'s "You cannot opt into any of these today
   except `unsupported_operation`" passage is replaced with the real mechanism and a worked
   example. That sentence is currently true; it must not survive as a stale falsehood.

## Non-goals
- No new error class — the six are settled.
- No provider adopting the mechanism. `P3-03` and Wave 5 do that.
- No CLI rendering change.
