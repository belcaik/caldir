**Provides:** — · **Needs:** `P3-02`

## Responsibility
A changed local task updates the *one* remote resource that already holds it. Nothing new is
invented: `find_event_location` already resolves `(uid, kind)` on both the `{uid}.ics` fast path and
the REPORT fallback, and `update_event` already sends a conditional `PUT` on the located ETag. This
ticket makes that path carry a task end to end and proves the property that matters — a second
resource is never created.

## Requirements satisfied
- **§8.2** — *"Updating a local task MUST update the existing remote resource rather than creating
  another remote task. The provider SHOULD reuse the same concurrency/ETag mechanisms currently
  used by VEVENT where applicable. A change to SUMMARY, DUE, STATUS, PRIORITY or another modelled
  task property MUST result in one updated remote VTODO."*
- **§8.4** — *"Provider-managed properties and unknown X-properties MUST follow the same
  preservation rules defined by `docs/vtodo/spec.md`."*
- **§7** — *"Local modification: local VTODO changed -> detect update -> provider update -> receive
  canonical remote representation -> update sync base"*. This ticket owns the "receive canonical
  remote representation" half at the provider boundary.

Proves **`CALDAV-3`** (*"Changing SUMMARY locally updates the same remote object"*), **`CALDAV-4`**
(`DUE`), and **`CALDAV-5`** (*"Changing STATUS to COMPLETED is reflected remotely"*).

## RED tests
All new, in `caldir-provider-caldav/src/caldav/ops/update_event.rs`'s test module (which does not
exist yet — create it, mirroring `create_event.rs`'s). `wiremock` is already a dev-dependency.

- **ADD** `caldav::ops::update_event::tests::updating_a_task_puts_once_to_the_resource_that_already_holds_it`.
  The `calendar-multiget` double returns the task at `{uid}.ics` with ETag `"t-1"`. Asserts:
  exactly one `PUT`; at `/cal/{uid}.ics`; with `If-Match: "t-1"`; with **no** `If-None-Match`; body
  containing `BEGIN:VTODO` and not `BEGIN:VEVENT`. Right proof because §8.2's failure mode is a
  *second* resource, and only a count assertion catches it — content assertions pass happily while
  a duplicate sits beside the original.
- **ADD** `caldav::ops::update_event::tests::a_changed_summary_due_status_or_priority_all_reach_the_one_resource`.
  Four sub-cases over the four properties §8.2 names, each starting from the same server-held task
  and changing exactly one field. Asserts, per sub-case, one `PUT` whose body carries the new value
  and no other property's value changed. Right proof because `CALDAV-3`, `CALDAV-4` and `CALDAV-5`
  are three separate acceptance IDs over one code path — proving one and assuming the rest is how a
  `STATUS` that never serializes ships green. `PRIORITY` is included because `Todo::priority` is a
  raw `i32` that must not be routed through `icalendar::Component::priority()`.
- **ADD** `caldav::ops::update_event::tests::an_update_never_lands_on_a_same_uid_event`.
  A `VEVENT` sharing the UID sits at `{uid}.ics`; the `calendar-query` double answers with the
  task at a server-assigned href. Asserts the single `PUT` targets the server-assigned href, and
  that the REPORT body contains `<C:comp-filter name="VTODO">`. Right proof: the fast path returns
  `None` for the wrong kind *today*, and this is the test that stops the item-typed rewrite from
  passing a constant kind — which would silently PUT a task over a meeting.
- **ADD** `caldav::ops::update_event::tests::update_returns_the_task_the_server_holds_not_the_one_sent`.
  The post-PUT `calendar-multiget` returns a `VTODO` whose `SUMMARY` differs from what was sent and
  which carries a server-only `X-` property. Asserts the returned `CalendarItem` is that `Todo`.
  Right proof: the read-back arm here is the same `CalendarItem::Event(..)` pattern as in
  `create_event`, with the same silent fall-through to `Ok(event)`, and this is the value `P2-02`
  stores as the sync base. Getting it wrong means every second sync reports a change forever.

## Acceptance criteria
1. Updating a task issues exactly one `PUT`, to the href `find_event_location` resolved for
   `(uid, ComponentKind::Todo)`, conditional on that location's ETag. (§8.2)
2. No update ever creates a second remote resource for the same `(uid, kind)`. Asserted by count,
   not by content. (§8.2, INDEX §4 P3-03 risk)
3. Changes to `SUMMARY`, `DUE`, `STATUS` and `PRIORITY` each reach the remote body.
   (`CALDAV-3`, `CALDAV-4`, `CALDAV-5`)
4. The kind passed to `find_event_location` comes from the item being written, never a constant;
   the UID-lookup REPORT filters on `VTODO` for a task and `VEVENT` for an event and carries no
   `<C:time-range>`. (R60, R61)
5. The post-PUT read-back returns the server's item for a task as it does for an event. (§8.4, §7)
6. `create_event`'s `409` fallback still delegates here and still runs at most once. (`P3-02` AC 4)
7. `find_event_location_is_component_aware_on_both_paths` and the byte-identical event REPORT lock
   stay green and unmodified. (`CALDAV-8`, §18)
8. `just check` green; `cargo test -p caldir-provider-caldav` green. (§24)

## Non-goals
- **No ETag-as-no-op reasoning.** R31: caldir re-stamps `DTSTAMP` on every serialize, so an
  unchanged ETag is not available as evidence of anything. Never assert on one as proof of a no-op.
- **No sync-base storage.** Storing what the provider returned is `P2-02`, in `caldir-core`.
- **No `X-` property merge.** INDEX §3 **C-13** — merging provider-managed `X-` properties from the
  previous state into an update — happens in `Remote::apply_change` before the RPC leaves core
  (`Event::with_x_properties_merged_from`), and extending it to `Todo` is `P2-01`'s. This ticket
  writes the item it is handed; it must simply not *drop* the `X-` properties on that item.
- **No create, no delete.** `P3-02` and `P3-04`.
- **No property enumeration.** `P3-06` owns "every modelled property survives".
- **No live server.** `P3-07`.
- **Do not modify `find_event_location`'s behaviour.** It is already component-aware on both paths
  and has a four-case lock. This ticket consumes it.
- **No conflict-resolution policy.** Which side wins is core's three-way base comparison
  (`caldir-core/src/diff/calendar_diff.rs`, `update_direction`); the provider writes what it is told
  to write.

## Notes for the implementer
- **`update_event.rs` has no test module today.** Create one modelled on `create_event.rs`'s: reuse
  `crate::caldav::ops::test_dav::{calendar_url, mount_report, multistatus, received_bodies}` and a
  local `puts(&server)` helper filtering `request.method == http::Method::PUT`.
- **Two `mount_report` markers do different jobs.** `"calendar-multiget"` answers the fast-path
  lookup and the post-PUT read-back; `"calendar-query"` answers the UID-lookup fallback. Mounting
  only one gives you a test that passes for the wrong reason.
- **The read-back trap is the same one as in `P3-02`**, in a second file:
  `if let Ok(caldir_core::CalendarItem::Event(fetched_event)) = parse_item(..)`. Fix both or the
  update path silently returns the locally-sent item.
- **`Todo`'s `==` ignores `created`, `last_modified` and `sequence`** (`educe(PartialEq(ignore))`).
  That is the right comparison for "did the update land" and the wrong one for "did the server
  bump the sequence" — do not build a sequence assertion on it.
- **C-13's failure mode reaches this file as a symptom, not a cause.** If a task update arrives
  with its provider-managed `X-` properties already stripped, the resource still updates and every
  test here passes; the damage shows up as a lookup failure on the *next* sync. If you see that,
  the fix is in `P2-01`, not here.
- `location_at_href` returns `None` for *not found, undecodable, or wrong component* alike, on
  purpose: it never hands back an href whose contents it has not identified. Preserve that.
- Conventions: raw `\r\n` ICS constants inline; the remote's bytes are always hand-written XML/ICS,
  never values re-encoded by the code under test; no ticket identifiers in shipped doc comments.
